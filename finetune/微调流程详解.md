# 第 0 章 先搞懂：我们在干什么

## 一句话

我们这个项目叫「掌柜问数」，功能是：**你用中文问一句，它自动写成 SQL 去数据库查，然后把数据给你。**

但这个能力目前是**靠调用云端大模型 API**（DeepSeek）实现的。我们要做的是：

> **把「写 SQL」这件事，从"调用云端大模型"换成"我们自己微调出来的小模型"。**

## 为什么要做

| 原因 | 说明 |
|---|---|
| 作业要求 | 课程要求做一次模型微调 |
| 效果提升 | 通用模型不懂我们库的业务口径，微调后能学会 |
| 成本 | 微调后的 8B 小模型可以自己部署，不按次付费 |

## 微调到底是什么（打个比方）

想象你要教一个刚毕业的实习生做数据分析：

- **不微调**：每次干活前，你都给他一份厚厚的《业务手册》，让他现学现做 —— 手册很长，他经常看漏。
- **微调**：让他**做 600 道练习题**，做完他就把这套业务的套路记住了。以后不用给那么详细的提示，他也能直接上手。

**微调 = 用「题目 + 标准答案」的例子，让模型学会特定任务的套路。**

## 具体到我们这件事

| 角色 | 对应什么 |
|---|---|
| 实习生 | Qwen3-8B（阿里开源的大模型，8B = 80 亿参数） |
| 练习题 | 616 条「问题 + 对应的标准 SQL」 |
| 老师批改 | 每条标准 SQL 都用数据库 `EXPLAIN` + 实际执行验证过 |
| 考试 | 115 条评测题，对比微调前后的准确率 |

**关键点**：我们不改变模型结构，只给它"加一层薄薄的适配层"（叫 LoRA），这样训练快、省钱、显存要求低。

# 第 1 章 名词速查

看不懂的术语回来查这里。

| 术语 | 大白话解释 |
|---|---|
| **微调 / Fine-tuning** | 拿现成的大模型，用你自己的数据再训练一下，让它学会你的任务 |
| **基座模型 / Base Model** | 拿来微调的那个"原始模型"。我们用的是 Qwen3-8B |
| **LoRA** | 一种省钱的微调方式。不改动原模型的 80 亿参数，只额外训练一小层（我们只训了 4364 万个参数，占 0.53%） |
| **QLoRA** | LoRA 的省显存版本（把权重压成 4bit）。**我们没用**，用的是更高精度的 bf16 |
| **bf16** | 一种数字格式（16 位浮点）。比 fp16 数值范围大、训练更稳 |
| **epoch** | 把全部训练数据完整看几遍。我们跑了 3 遍 |
| **loss** | 损失，衡量"模型答得有多差"。越低越好 |
| **eval_loss** | 在**没用来训练**的验证集上的 loss，用来判断有没有"死记硬背" |
| **过拟合** | 模型把训练数据背下来了，遇到新题就不会了。表现为 train_loss 低但 eval_loss 高 |
| **checkpoint** | 训练过程中的存档点。中途挂了可以接着跑 |
| **推理 / Inference** | 用训练好的模型去回答问题（区别于"训练"） |
| **EX（执行准确率）** | 模型生成的 SQL 跑出来的结果，和标准答案的结果**是否一致**。这是我们的核心指标 |
| **SSE** | 服务器推送事件，一种流式返回数据的技术。我们的接口用它实时返回进度 |
| **schema** | 数据库的表结构信息（有哪些表、哪些字段、字段什么意思） |
| **EXPLAIN** | MySQL 的一个命令，能"预演"一条 SQL 而不真正执行，用来检查语法对不对 |

# 第 3 章 阶段一：准备评测集

## 目标

造 115 道题，每题带标准答案，且**标准答案必须能真正执行**。

## 为什么不能"让大模型随便编标准答案"

这是最容易踩的坑：

> 如果你让大模型凭空编 SQL 当标准答案，编出来的 SQL **可能根本跑不通**，也可能**跑得通但口径是错的**。
> 那就等于**用幻觉当标准答案** —— 后面算出来的"准确率"毫无意义。

## 我们的做法：模板抽样 + 数据库硬校验

```
真实的数据库建表脚本（dw.sql，含真实的省份/品牌/品类等数据）
        ↓
gen_eval_set.py  按 6 项能力套模板生成题目和标准 SQL
        ↓
validate_sql.py  在 SQLite 影子库里逐条执行，跑不通就报错
```

**核心思想**：题目里的业务实体（省份、品牌、品类）都是**数据库里真实存在的**，标准 SQL 由模板套出来，再用数据库验证 —— 不需要人写，但答案是硬的。

## 命令

```bash
cd data-agent

# ① 生成 115 道题
python finetune/gen_eval_set.py

# ② 校验标准 SQL 能否执行（应输出 93/93 全部通过）
python finetune/validate_sql.py
```

## 成功长什么样

```
[1/4] 解析真实数仓结构: ...\dw.sql
      地区 6 个 | 商品 15 个 | 客户 20 个 | 日期 90 天 (20250101~20250331)
[2/4] 由模板生成样本
      SQL 类模板产出 98 条 | 澄清类 18 条
[3/4] 已写出 115 条 -> finetune\data\test.jsonl
```

校验脚本应该输出：
```
      可执行且有结果 : 93
      可执行但结果为空: 0
      执行失败        : 0
  全部标准 SQL 均可执行 ✅
```

## 按作业要求的分层

| 作业能力 | 条数 |
|---|---|
| 3.2.1 业务问题到字段映射 | 7 |
| 3.2.2 字段值识别与标准化 | 24 |
| 3.2.3 指标口径理解与计算 | 14 |
| 3.2.4 查询意图澄清 | 18 |
| 3.2.5 多表关联与查询条件生成 | 47 |
| 3.2.6 SQL 安全与方言适配 | 5 |
| **合计** | **115** |

# 第 4 章 阶段二：准备训练数据

微调需要「题目 + 标准答案」。我们准备了**三类**数据，因为微调要解决三类不同的问题。

## 类别一：问数 → SQL（主任务，424 条）

**解决什么**：把中文问题翻译成正确的 SQL。

**怎么来**：把语料里的问题，配上真实 schema，让云端大模型（DeepSeek）生成 SQL，**能通过 EXPLAIN + 实际执行的才保留**。

```bash
# 先生成问题语料（1035 条）
python finetune/make_corpus.py

# 再合成训练数据（并发调用，约 15 分钟）
python finetune/synthesize_train_data.py --target 500 --concurrency 8
```

**为什么用"合成"而不是跑完整流水线**：跑完整流水线每条要 5 次大模型调用、约 25 秒，1000 条要 7 小时。而实际上那 5 次调用里**有 4 次只是在"找该用哪些表"**，只有最后 1 次是真正要训的"写 SQL"。因为我们的库只有 5 张表，"找表"这一步可以直接省掉。

> 实测：合成约 **1.8 秒/条**，比流水线的 25 秒/条快 14 倍。

## 类别二：错误 SQL → 修正 SQL（541 条）

**解决什么**：SQL 写错了要能改对。

**为什么需要单独造**：模型很少自然写错，所以**采集不到**"错误 → 修正"这种配对。

**怎么造**：从正确 SQL 出发，**故意注入典型错误**，再用数据库 `EXPLAIN` 跑一遍拿到**真实报错**：

```
正确：SELECT SUM(f.order_amount) FROM fact_order f ...
  ↓ 注入错误（把 order_amount 改成 order_emount）
错误：SELECT SUM(f.order_emount) FROM fact_order f ...
  ↓ 送进 EXPLAIN，拿真实报错
报错：(1054, "Unknown column 'f.order_emount' in 'field list'")
  ↓ 配对
训练样本：(错误SQL + 真实报错) → 正确SQL
```

**为什么可靠**：报错是**数据库真实返回的**，不是编的。而且能通过 EXPLAIN 的"假错误"会被丢弃。

```bash
python finetune/build_correct_sql_data.py
```

产出 5 种错误类型：语法错误 151 / 表名拼错 121 / 字段名拼错 119 / 别名未定义 108 / 聚合函数用错 42。

## 类别三：澄清与拒答（33 条）

**解决什么**：
- 用户问「销售怎么样？」这种**信息不全**的问题时，应该**反问**而不是瞎猜
- 用户要求「把商品删掉」这种**危险请求**时，应该**拒绝**

**这是现有系统最大的能力缺口** —— 实测基线在这个指标上是 **0%**。

**怎么造**：机械反向变换。标准 SQL 里必然带有时间条件、分组维度、聚合口径，**逐一摘掉**就得到了"信息不全"的问题：

```
原题：2月的销售额是多少？          （信息完整）
  ↓ 摘掉时间条件
新题：销售怎么样？                 （信息不全 → 应该反问）
```

```bash
python finetune/make_negatives.py
```

## 合并成最终训练集

```bash
python finetune/build_final_train_set.py
```

这一步会做三件重要的事：

1. **统一 system 提示词** —— 原来三类数据的 system 不一致，模型会学乱
2. **给澄清样本补 schema** —— 原来澄清样本的输入里**没有 schema**，模型会学成"没有 schema 就反问"，而线上永远有 schema，于是永远不反问
3. **配比平衡** —— `correct_sql` 原本占 54%，会喧宾夺主，降采样到 31.7%

**最终产出**：

```
finetune/data/
├── train_final.jsonl     616 条训练
├── val_final.jsonl        53 条验证
└── dataset_info.json      LLaMA-Factory 的数据注册文件
```

## 数据长什么样

每条训练样本是三段对话：

```
【system】固定不变的角色说明（含"信息不足要反问"的约定）
【human】 = 【可用数据表信息】+【指标信息】+【当前时间】+【数据库环境】+【用户查询】
【gpt】  = 标准答案（一条 SQL，或一段澄清/拒答的话）
```

**模型要学的是**：看到这样的输入，输出那样的答案。

# 第 5 章 阶段三：租卡与装环境

## 为什么要租卡

你本机的显卡是 8GB 显存，**跑不动 8B 模型的训练**（需要 30GB+）。

## 租什么卡

| 项目 | 要求 | 我们实际用的 |
|---|---|---|
| 显存 | **≥ 40GB**（bf16 训练 8B 模型） | RTX PRO 6000，96GB |
| 硬盘 | 数据盘 ≥ 50GB（模型 16G + 依赖） | 150GB |
| 时价 | — | ¥2.78/小时 |
| 总花费 | 预算 100 元 | **约 ¥10** |

**选卡要点**：
- 优先**预装 PyTorch 的镜像**（省 20–30 分钟配置）
- **显存比算力重要** —— 显存不够直接 OOM 跑不了
- 别忘了看**数据盘大小**，模型 16G 加依赖很容易超

## 装环境（在租卡机器的终端里）

### ① 下载模型

```bash
pip install modelscope -q
mkdir -p /root/autodl-tmp/models
modelscope download --model Qwen/Qwen3-8B --local_dir /root/autodl-tmp/models/Qwen3-8B
```

> 用 `modelscope`（国内）而不是 HuggingFace（国外，很慢）。
> **一定放 `/root/autodl-tmp/`** —— 这是数据盘，关机不丢；系统盘只有 30G，装不下。

### ② 装 LLaMA-Factory

```bash
pip install llamafactory -i https://pypi.tuna.tsinghua.edu.cn/simple
llamafactory-cli version      # 应输出 0.9.5
```

> **不要用 `git clone`**！GitHub 在国内只有 20KB/s，会下几个小时。
> PyPI + 清华源是 MB/s 级别。

### ③ 修 torch 版本（这一步很容易踩坑）

`pip install llamafactory` 可能把 `torchaudio` 升到一个和 CUDA 不匹配的版本。验证：

```bash
python -c "import torch, torchaudio; print(torch.__version__, torchaudio.__version__, torch.cuda.is_available())"
```

**正常应该看到** `cuda True` 和三个版本配套。

**如果报 `libcudart.so.13: cannot open shared object file`**，说明版本错配，修：

```bash
pip install torch torchvision torchaudio \
  --index-url https://download.pytorch.org/whl/cu128
```

> 注意是 `--index-url`（指定 PyTorch 官方源）而不是 `-i`（换源）。
> 国内镜像**没有** cu128 的轮子，用 `-i` 装不到。

### ④ 上传数据

把本机的这些文件传到租卡机器：

| 本机文件 | 传到哪 |
|---|---|
| `finetune/data/train_final.jsonl` | `/root/autodl-tmp/data/` |
| `finetune/data/val_final.jsonl` | `/root/autodl-tmp/data/` |

# 第 6 章 阶段四：训练

## 训练配置的关键参数

文件：`train_qwen3_8b_lora.yaml`

```yaml
model_name_or_path: /root/autodl-tmp/models/Qwen3-8B
finetuning_type: lora          # 用 LoRA（省钱）
lora_rank: 16                  # 适配层的大小，数据少所以不用太大
lora_target: all               # 对所有线性层加 LoRA
dataset: zhangguiwenshu_sft
template: qwen3                # Qwen3 的对话模板
cutoff_len: 4096               # 单条样本最长 token 数（schema 很长，不能太小）
per_device_train_batch_size: 2
gradient_accumulation_steps: 8 # 等效 batch = 2 × 8 = 16
learning_rate: 1.0e-4
num_train_epochs: 3.0          # 数据少，跑 3 轮
bf16: true                     # 16 精度（这就是"不要 4 精度"的落点）
gradient_checkpointing: true   # 用时间换显存
```

## 开训

```bash
cd /root/autodl-tmp
nohup llamafactory-cli train /root/autodl-tmp/train_qwen3_8b_lora.yaml > train.log 2>&1 &
tail -f train.log
```

> `nohup ... &` 让训练在后台跑，**断开 SSH 也不会中断**。
> `tail -f` 只是看日志，可以随时 Ctrl+C 退出（不影响训练）。

## 成功长什么样

开头会看到：
```
trainable params: 43,646,976 || all params: 8,234,382,336 || trainable%: 0.5301
Num examples = 616
Total train batch size = 16
Total optimization steps = 117
```

**三个关键数字**：
- `trainable params` ≈ 4364 万 → LoRA 挂上了（如果是 0 说明没生效）
- `Num examples = 616` → 数据读对了
- `Total optimization steps = 117` → 616 / 16 × 3 = 115.5，对得上

训练过程中：
```
{'loss': 1.23, 'epoch': 0.26}
{'loss': 0.45, 'epoch': 1.5}
...
```

## 训练结果（我们的实测）

| 指标 | 值 | 说明 |
|---|---|---|
| train_loss | **0.2221** | 从 1.x 降下来 |
| **eval_loss** | **0.0933** | **比 train_loss 还低 → 没有过拟合** ✅ |
| 耗时 | 33 分钟 | |
| GPU | RTX PRO 6000 | |

**怎么判断训练好不好**：

| 现象 | 判断 |
|---|---|
| train_loss 和 eval_loss 都在降 | ✅ 正常 |
| train_loss 很低，eval_loss 却先降后升 | ❌ 过拟合，减少 epoch |
| loss 一直不动（卡在 1.x） | ❌ 学习率或数据有问题 |

## 导出合并模型

训练产出的是**独立的 LoRA 适配层**（几十 MB）。为了方便后续预测，把它和基础模型合并成一个完整模型：

```bash
cat > /root/autodl-tmp/export_qwen3_8b.yaml << 'EOF'
```

# 第 7 章 阶段五：预测与评测

## 这一阶段在干什么

要证明"微调有效"，必须**对比**：

| 配置 | 说明 |
|---|---|
| **基线**：原版 Qwen3-8B（未微调） | 对照组 |
| **实验组**：微调后的 Qwen3-8B | 要证明它更好 |

**两者必须用完全相同的题目和上下文**，否则差异无法归因。

## 关键难点：检索服务只在本地

预测需要「schema 上下文」，而 schema 来自检索链路（MySQL + Qdrant + ES + Embedding）—— **这些服务只在你的本机，租卡机器上没有**。

**解决**：本机先把 115 道题的 schema 导出成文件，上传到租卡机器，那边就能脱离检索服务直接推理。

```bash
# 本机执行（约 30 分钟）
python finetune/dump_context.py
# → finetune/data/eval_context.jsonl
```

> **为什么跳过 LLM 过滤节点**（`--fast`，默认开启）：
> 流水线里 `filter_table`/`filter_metric` 会再调两次大模型裁剪 schema，但
> ① 极慢（3 小时+）；② 它有时会裁掉 JOIN 需要的维表，导致"模型答错"和"过滤裁错"两个变量混在一起。
> 跳过后 base 和微调模型用**完全相同的上下文**，对比更干净。

## 跑两次预测（在租卡机器上）

把 `eval_context.jsonl`、`predict_with_model.py` 上传到租卡机器，然后：

```bash
# ① 原版模型
python predict_with_model.py \
    --model /root/autodl-tmp/models/Qwen3-8B \
    --context /root/autodl-tmp/data/eval_context.jsonl \
    --out /root/autodl-tmp/preds/base.jsonl

# ② 微调后模型
python predict_with_model.py \
    --model /root/autodl-tmp/output/qwen3-8b-merged \
    --context /root/autodl-tmp/data/eval_context.jsonl \
    --out /root/autodl-tmp/preds/lora.jsonl
```

每个约 10–15 分钟。跑完把两个 jsonl 下载回本机。

## 算指标（在本机）

```bash
python finetune/eval_ex.py --db mysql \
    --predictions finetune/data/preds/base.jsonl \
    --name "基线：Qwen3-8B 原版"

python finetune/eval_ex.py --db mysql \
    --predictions finetune/data/preds/lora.jsonl \
    --name "微调后：Qwen3-8B LoRA"
```

## 三层指标是什么意思

| 层级 | 指标 | 含义 |
|---|---|---|
| **L1** | 可执行率 | 生成的 SQL 能不能跑通（不报语法错） |
| **L2** | **执行准确率 EX** | SQL 跑出来的**结果集**和标准答案是否一致 |
| **L3** | 澄清/拒答准确率 | 该反问时有没有反问、该拒绝时有没有拒绝 |

**为什么用"结果集比对"而不是"SQL 文本比对"**：
同一个业务问题有多条等价 SQL（JOIN 顺序不同、别名不同），文本比对会误判。**用户要的是数据，不是某种特定写法。**

# 第 8 章 踩过的坑（真实记录）

这部分**对交付文档很重要** —— 说明我们不是一路顺风，而是真的踩过并解决了。

## 坑 1：评测集标注自相矛盾

**现象**：评测器自检时报 93/97，不是满分。

**原因**：4 条危险请求被标成 `expected_type="SQL"` 却 `reference_sql=None` —— 自相矛盾，导致"正确拒答"被判为失败。

**修复**：类型由"是否给出标准 SQL"决定，并新增 `refuse` 字段区分"应拒答"和"应澄清"。

**怎么发现的**：靠评测器的 `--pred-from-ref` 自检（用标准答案当预测，应该 100%）。

## 坑 2：合成数据的 SQL 语法错

**现象**：`validate_sql.py` 报 37 条 SQL 执行失败，`WHERE p.category = ''手机数码''` 多了一层引号。

**原因**：解析 `dw.sql` 时用了贪婪正则 `[^']+`，把 `'P001', 'iPhone 15 Pro'` 整段吞掉，只有第一个值被正确去引号。

**修复**：改成从左到右的字符扫描。

**教训**：**如果没做执行校验，这 37 条标准答案就全部作废了** —— 印证了"答案必须可被机器验证"。

## 坑 3：训练数据里混入了"臆造年份"的 SQL

**现象**：合成数据里有 70 条带 `WHERE year = 2026`，而数据库只有 2025 年数据。

**原因**：语料里的问题**没提年份**，但模型看到系统提示词里的"当前时间 2026-09"，就自己加了个 `year = 2026`。这属于**过度限定**，必然查空。

**为什么校验没拦住**：我原本的判断是"结果为空就丢弃"，但 `SELECT SUM(...)` 匹配不到行时返回的是**一行 NULL**，不是空列表 —— `if not rows` 判不出来。

**修复**：判断"结果集全为 NULL"也算无效，并显式拒绝数据范围外的年份过滤。

## 坑 4：负样本的输入格式是错的

**现象**：澄清/拒答样本的 `human` 段**只有**「【用户查询】看看销售情况」，**没有 schema**。

**后果（很严重）**：模型会学到"**没有 schema → 就反问**"。而线上任何请求都带 schema，于是它**永远不反问** —— 澄清能力根本学不到。

**修复**：合并训练集时给负样本补上与其它样本一致的完整上下文。

## 坑 5：三类数据的 system 提示词不一致

**现象**：`train_synth` 的 system 只让"输出 SQL"，`negatives` 的 system 却追加了"信息不足要反问"。

**后果**：同一份 system 却要求两种相反行为，模型会学乱。

**修复**：全部统一为含澄清约定的那一版。

## 坑 6：去重去过头

**现象**：1011 条合并数据被去重到 578 条。

**原因**：`correct_sql` 里同一个问题有 **5 种不同错误类型**（我故意注入 5 种），却按"任务+问题"去重，把 537 条纠错样本误并成 121 条。

**修复**：纠错样本按"**错误 SQL**"去重，而不是按"问题"。

## 坑 7：pip 装 LLaMA-Factory 装出 CUDA 版本错配

**现象**：
```
pip install llamafactory        → 成功
llamafactory-cli train ...      → OSError: libcudart.so.13: cannot open shared object file
```

**原因**：pip 把 `torchaudio` 升到了针对 **CUDA 13** 编译的 2.11.0，而机器的 PyTorch 是 **CUDA 12.8** 版本。torch / torchvision / torchaudio **三者必须严格配套**。

**修复**：
```bash
pip install torch torchvision torchaudio \
  --index-url https://download.pytorch.org/whl/cu128
```
用 **PyTorch 官方源**（`--index-url`，不是 `-i`），三个包会装成配套版本。

**中途还遇到**：用了 `--no-deps` 导致缺 `libnvshmem_host.so.3` —— 去掉 `--no-deps` 后 pip 会把 nvidia 系列依赖一起装上。

## 坑 8：git clone LLaMA-Factory 慢到不可用

**现象**：`git clone` 只有 **19 KB/s**，估计要几小时。

**原因**：GitHub 在国内被限速。

**修复**：改用 `pip install llamafactory -i 清华源`，走 PyPI，MB/s 级别，几分钟装完。

## 坑 9：评测要连 MySQL，但本机 3306 被占用

**现象**：应用连不上数据库，报 `Access denied for user 'appuser'@'172.21.0.1'`。

**排查过程（这里我走了弯路）**：我以为是密码错，猜了十几次密码、还重置了账号 —— **全是无用功**。

**真正原因**：项目代码 `MysqlClientManager._get_url()` **手拼连接串时漏掉了 `port`**：

```python
# 有 bug 的版本（没有 port，永远连默认 3306）
f"mysql+asyncmy://{user}:{password}@{host}/{database}?charset=utf8mb4"
```

于是配置里的 3307 根本不生效，永远去连 3306 —— 而 3306 上是**另一个项目的 MySQL**，自然认证失败。

**修复**：改用 SQLAlchemy 的 `URL.create()`，显式带上端口（同时正确处理密码里的特殊字符）。

**教训**：**报错信息会骗人**。`Access denied` 看起来像密码问题，实际是连错了服务器。应该先确认"到底连到了哪里"，而不是急着改密码。

## 坑 10：`localhost` 与 `127.0.0.1` 不等价

**现象**：数据库配置里写 `localhost` 连不上，写 `127.0.0.1` 就行。

**原因**：Windows 上 `localhost` 会优先解析成 **IPv6 的 `::1`**，走的网络路径和 IPv4 不同，连不上 Docker 映射的端口。

**修复**：配置里统一用 `127.0.0.1`。

## 附：一句话记住整个流程

> **造题（带硬校验）→ 造答案（让云端模型生成+验证）→ 教模型（LoRA 微调）→ 考试（同题目同上下文对比）**

核心原则就三条：
1. **答案必须能被机器验证** —— 不靠人肉检查，也不靠模型自我声称
2. **对比必须只变一个变量** —— base 和微调模型用完全相同的输入
3. **每一步都留证据** —— 中间产物全部落盘，出问题能回溯
