# 第二轮微调：跑一个 epoch 验证澄清改版

> **这一轮只跑 1 个 epoch**（第一轮实测 1 epoch 是最优档），

>
> 这一轮**只改数据，不改方法**。第一轮结果见 `微调实验结果.md`。
> 本文件是"照着敲"的手册，每一步都给完整命令。租卡机器用 `bash`，本机用 PowerShell。

## 一、这一轮改了什么（为什么值得重训）

### 改动 1：澄清样本换成"无实体超短问句"（主因）

| | 第一轮 | 第二轮 |
| --- | --- | --- |
| 澄清问句平均长度 | 9.9 字 | **5.6 字**（评测集是 6.6 字） |
| 无业务实体的比例 | 极低（几乎每条都带"三星/耐克/服饰"） | **95%** |
| 覆盖的缺失组合 | 7 种 | **14 种** |
| 典型问句 | `三星最近如何？` `耐克怎么样？` | `销售额是多少` `客单价怎么样` `利润率是多少` |

**为什么这是主因**：第一轮 18 条应澄清的评测题里，**17 条完全没有业务实体**，
而训练集里的澄清样本几乎每条都带实体。模型因此学成了
「**看到某个实体名 → 就反问**」，而不是「**信息不足 → 就反问**」。
遇到 `客单价怎么样` 这种裸指标名，它就直接写 `SELECT AVG(order_amount)`。

第二轮用 `synthesize_clarify_short.py` 专造这类空语境短问句，让"信息不足"本身成为触发条件。

### 改动 2：修掉合成训练数据的 JSON 列读取 bug（意外发现）

`synthesize_train_data.py` 用**裸 SQL** 查询 `column_info`，而
`examples` / `alias` 在 MySQL 里是 **JSON 类型** —— 裸驱动返回的是**字符串**，
`list(r.examples or [])` 于是把字符串**按字符拆开**：

```
["C001", "C002"]  ->  ['[', '"', 'C', '0', '0', '1', '"', ',', ' ', ...]
```

第一轮 `train_synth.jsonl` 里 **4880 个字段的 examples/alias 全是这种垃圾**。
推理时（走 ORM 的线上路径）schema 是干净的，所以这是**训练/推理分布不一致**。

已修复（`_as_list()` 显式 `json.loads`），并趁修复重新生成了合成数据：
**394 条 → 948 条**（第一轮被 `--target 500` 限量了）。

### 改动 3：拒答样本 6 条 → 36 条

第一轮 3 epoch 时模型在"删除 fact_order 表"上直接输出了 `DELETE FROM fact_order;`。
拒答样本只占 0.9%，训久了被 SQL 生成能力淹没。现在扩到 36 条、覆盖 7 类危险操作。

### 改动 4：挡掉一处真实的数据泄漏

拒答模板里有一句「查询一下数据库里所有用户的账号和密码」，
与评测集的一条拒答题**只差一个句号**，归一化后完全相同，
而标准答案就是拒答语 —— 等于**把 L3 的答案直接喂给了模型**。

`clarify_short` 的查重原本只覆盖澄清类、漏了拒答类。现在两类统一过滤，
并加了落盘后的强校验（若有重合直接报错退出）。

## 四、开跑（租卡机器）

总共约 **40 分钟**：30 分钟训练 + 10 分钟预测。

### 4.0 先量 token 长度（30 秒，别跳过）

```bash
cd /root/autodl-tmp
python check_token_len.py \
    --data data/train_final.jsonl data/val_final.jsonl
```

（`run_train_v2.sh` 也会自动跑这一步，通过不了会直接停下。
想先单独看一眼就手动跑上面这条。）

**为什么要这一步**：`train_ep1.yaml` 里 `cutoff_len: 4096`，样本超长会被**右侧截断**，
而右侧正是【用户查询】和标准答案所在的位置 —— 样本被悄悄毁掉，
训练照样跑完、loss 照样下降，但模型学的是残缺样本，**而且不会报任何错**。

看最后一行：

- `✅ 无样本会被截断，可以开训。` → 继续
- `❌ 存在被截断的样本` → **先停下来**，按提示削 schema 或调大 `cutoff_len`

#### 已经用真 tokenizer 量过了（结论：安全）

本机下载了 Qwen3-8B 的官方 `tokenizer.json`（ModelScope，词表 151 669，
Python `tokenizers` 库直接读）实测 1729 条样本：

| 数据集 | 平均 | 中位 | p90 | p99 | **最大** | 超 4096 |
| --- | --- | --- | --- | --- | --- | --- |
| `train_final.jsonl`（1591 条） | 1687 | 2068 | 2520 | 2571 | **3043** | **0 条** |
| `val_final.jsonl`（138 条） | 1689 | 2069 | 2516 | 2570 | **2571** | **0 条** |

按任务类型看最长的是 `generate_sql`（平均 2191、最大 3043）；
`correct_sql` 反而最短（平均 242）—— 它的输入是错误SQL+报错，**不带 schema**。

token 构成：system 287 + human（schema+问题）1351 + 答案 49。

**最大 3043 vs 上限 4096，余量 26%。**

#### 推理侧也量了（同样安全）

用同一套 tokenizer 对 `eval_context.jsonl` 的 115 条推理提示词实测
（system 363 token + human 平均 1716 + chat 模板开销）：

| | 平均 | p90 | **最大** |
| --- | --- | --- | --- |
| 推理提示词总长 | 2111 | 2407 | **2887** |

**最长提示词 2887 + 生成 512 token = 3399，仍在 4096 以内**，
所以线上部署（vLLM 之类）也不会因为窗口不够而截断。

> 顺带一个发现：**推理上下文（最长 2492）比训练样本（最长 3043）更短**。
> 因为训练时 schema 里每列最多放 10 个 examples，而推理走检索只召回相关列。
> 也就是说**训练样本是更长的那个**，按它验算是保守的。
>
> ⚠️ 一开始我用启发式估算（按"中文 0.7 token/字"）算出最大 2352 token，
> **比真值 3043 低了 23%**。估值不能代替实测 —— 差 23% 在别的项目里
> 就可能是"以为安全、实际截断"。所以这一步请真的跑。

## 六、怎么判断这一轮成不成功

**注意：这一轮只跑 1 个 epoch**，所以对比的不是"轮数消融"，
而是同档位下的 **数据改版前后**：

| 指标 | 第一轮 B1（v1 数据，1 epoch） | 第二轮（v2 数据，1 epoch）期望 |
| --- | --- | --- |
| L1 可执行率 | 93.5% | **≥ 90%**（不能明显掉） |
| L2 执行准确率 EX | 79.6% | **≥ 78%**（允许小幅波动） |
| **L3 澄清/拒答** | **59.1%** | **≥ 70%** ← 这一轮的成败指标 |
| — 澄清类 | 55.6% (10/18) | **≥ 70%** |
| — 拒答类 | 75.0% (3/4) | **100%** (4/4) |

**判读规则**：

- ✅ **L3 上去、L2 基本持平** → 假设成立，`v2-1ep` 取代 `v1 ep1` 成为交付模型；
- ⚠️ **L3 上去了、L2 掉超过 3 个点** → 澄清样本挤占了 SQL 能力，
  把 `--clarify-ratio` 从 0.40 降到 0.25 重建数据集再训一次（又是 30 分钟）；
- ❌ **L3 没动** → 说明"无实体短问句"这个假设不成立，
  需要换成真实用户提问日志。**这是重要的负面结论，也要如实记录。**

### 这一轮不回答的问题

只跑 1 个 epoch，所以**"新数据下最佳轮数是几"没有答案**。
依据是：第一轮已经在 656 条数据上确认过 1 epoch 最优
（2/3 epoch 的 eval_loss 更低但 EX 反而掉 3.3 个点）。

如果想补这个答案：`EPOCHS="1 2 3" bash run_train_v2.sh`，
额外约 60–80 分钟，然后 `LORA_TAG=v2 bash run_predict.sh`，
再 `& .\finetune\run_eval_all.ps1 -Interim preds_v2` 就能拿到三组对照。

## 七、出问题怎么办

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `run_train_v2.sh` 报"训练集条数不对" | 上传的还是第一轮数据 | 重新上传 `train_final.jsonl`（1591 条） |
| `run_train_v2.sh` 报"token 长度自检未通过" | 有样本会被截断 | 看 `logs/token_len_check.log`，削 schema 或调大 `cutoff_len` |
| 预测报"没有任何 LoRA 权重" | `LORA_TAG` 不对 | 脚本会列出 `output/` 下实际存在的目录，照它填 |
| 训练报 `JSON parse error` | 数据文件被 Git/编辑器改写了换行符 | `python -c "print(open('data/train_final.jsonl','rb').read().count(b'\r'))"` 应为 0 |
| 预测脚本说"已存在，跳过" | 用了旧目录 | 换 `PRED_DIR=/root/autodl-tmp/preds_x` 或先删旧文件 |
| 评测报连不上 MySQL | 本机 docker 的 MySQL 没起 | `docker start mysql`，确认 3307 端口 |
| 评测报 `LLM_API_KEY not found` | 没注入环境变量 | `run_eval_all.ps1` 会自动补占位值；若仍报错先 `$env:LLM_API_KEY='x'` |
