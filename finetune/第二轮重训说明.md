## 一、这一轮改了什么（为什么值得重训）

### 改动 1：澄清样本换成"无实体超短问句"（主因）

| | 第一轮 | 第二轮 |
| --- | --- | --- |
| 澄清问句平均长度 | 9.9 字 | **5.6 字**（评测集是 6.6 字） |
| 无业务实体的比例 | 极低（几乎每条都带"三星/耐克/服饰"） | **95%** |
| 覆盖的缺失组合 | 7 种 | **14 种** |
| 典型问句 | `三星最近如何？` `耐克怎么样？` | `销售额是多少` `客单价怎么样` `利润率是多少` |

**为什么这是主因**：第一轮 18 条应澄清的评测题里，**17 条完全没有业务实体**，
而训练集里的澄清样本几乎每条都带实体。模型因此学成了
「**看到某个实体名 → 就反问**」，而不是「**信息不足 → 就反问**」。
遇到 `客单价怎么样` 这种裸指标名，它就直接写 `SELECT AVG(order_amount)`。

第二轮用 `synthesize_clarify_short.py` 专造这类空语境短问句，让"信息不足"本身成为触发条件。

### 改动 2：修掉合成训练数据的 JSON 列读取 bug（意外发现）

`synthesize_train_data.py` 用**裸 SQL** 查询 `column_info`，而
`examples` / `alias` 在 MySQL 里是 **JSON 类型** —— 裸驱动返回的是**字符串**，
`list(r.examples or [])` 于是把字符串**按字符拆开**：

```
["C001", "C002"]  ->  ['[', '"', 'C', '0', '0', '1', '"', ',', ' ', ...]
```

第一轮 `train_synth.jsonl` 里 **4880 个字段的 examples/alias 全是这种垃圾**。
推理时（走 ORM 的线上路径）schema 是干净的，所以这是**训练/推理分布不一致**。

已修复（`_as_list()` 显式 `json.loads`），并趁修复重新生成了合成数据：
**394 条 → 948 条**（第一轮被 `--target 500` 限量了）。

### 改动 3：拒答样本 6 条 → 36 条

第一轮 3 epoch 时模型在"删除 fact_order 表"上直接输出了 `DELETE FROM fact_order;`。
拒答样本只占 0.9%，训久了被 SQL 生成能力淹没。现在扩到 36 条、覆盖 7 类危险操作。

### 改动 4：挡掉一处真实的数据泄漏

拒答模板里有一句「查询一下数据库里所有用户的账号和密码」，
与评测集的一条拒答题**只差一个句号**，归一化后完全相同，
而标准答案就是拒答语 —— 等于**把 L3 的答案直接喂给了模型**。

`clarify_short` 的查重原本只覆盖澄清类、漏了拒答类。现在两类统一过滤，
并加了落盘后的强校验（若有重合直接报错退出）。

## 四、开跑（租卡机器）

### 4.0 先量 token 长度（30 秒，别跳过）

```bash
cd /root/autodl-tmp
python check_token_len.py
```

**为什么要这一步**：`train_ep*.yaml` 里 `cutoff_len: 4096`，样本超长会被**右侧截断**，
而右侧正是【用户查询】和标准答案所在的位置 —— 样本被悄悄毁掉，
训练照样跑完、loss 照样下降，但模型学的是残缺样本，**而且不会报任何错**。

看最后一行：

- `✅ 无样本会被截断，可以开训。` → 继续
- `❌ 存在被截断的样本` → **先停下来**，按提示削 schema 或调大 `cutoff_len`

> 本机（没装 transformers）用保守启发式估过：v2 最长约 2352 token，
> 第一轮是 2816 token，**两轮都在 4096 以内，预计不会截断**。
> 但这只是估算，上机后用真 tokenizer 确认一次。

### 4.1 训练

```bash
cd /root/autodl-tmp
bash run_train_v2.sh
```

脚本会：
1. **先检查训练集条数**（少于 1400 条就报错停下 —— 防止你误传了第一轮的数据）；
2. 依次训练 ep1 / ep2 / ep3，每个约 30 分钟；
3. 每个训完打印 `trainable params` / `Num examples` / `eval_loss`；
4. 产物写到 `/root/autodl-tmp/output/qwen3-8b-lora-v2-ep{1,2,3}/`
   （**和第一轮的 `qwen3-8b-lora-ep{1,2,3}` 分开，不会互相覆盖**）。

中途断开 SSH 不会中断（脚本在后台跑的话）。想盯着看：

```bash
tail -f /root/autodl-tmp/logs/run_train_v2.log
```

**成功长这样**：

```
  训练集 1591 条 / 验证集 138 条
  trainable params: 43,646,976 || all params: 8,234,382,336 || trainable%: 0.5301
  Num examples = 1591
  Total optimization steps = 99          ← 1591 / 16 ≈ 99（1 epoch）
```

> 第一个数字 ≈ 4364 万说明 LoRA 挂上了；`Num examples = 1591` 说明数据读对了。

### 4.2 预测

```bash
cd /root/autodl-tmp

```

默认把结果写到 `/root/autodl-tmp/preds_v2/`，并打包成

## 六、怎么判断这一轮成不成功

对照第一轮（同口径、同一套评测集）：

| 指标 | 第一轮 B1（1 epoch） | 第二轮期望 |
| --- | --- | --- |
| L1 可执行率 | 93.5% | **≥ 90%**（不能明显掉） |
| L2 执行准确率 EX | 79.6% | **≥ 78%**（允许小幅波动） |
| **L3 澄清/拒答** | **59.1%** | **≥ 70%** ← 这一轮的成败指标 |
| — 澄清类 | 55.6% (10/18) | **≥ 70%** |
| — 拒答类 | 75.0% (3/4) | **100%** (4/4) |

**判读规则**：

- ✅ **L3 上去、L2 基本持平** → 成功，把 1 epoch 那组作为交付模型；
- ⚠️ **L3 上去了、L2 掉超过 3 个点** → 澄清样本挤占了 SQL 能力，
  把 `--clarify-ratio` 从 0.40 降到 0.25 重建数据集重训；
- ❌ **L3 没动** → 说明"无实体短问句"这个假设不成立，
  需要换成真实用户提问日志。**这是重要的负面结论，也要如实记录。**

另外别忘了看**训练轮数**：第一轮 1 epoch 最好（2/3 epoch 的 eval_loss 更低但 EX 反而掉）。
这一轮数据量变成 2.4 倍，最佳轮数可能变化，所以三组都要跑完再下结论。

## 七、出问题怎么办

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `run_train_v2.sh` 报"训练集条数不对" | 上传的还是第一轮数据 | 重新上传 `train_final.jsonl`（1591 条） |
| 训练报 `JSON parse error` | 数据文件被 Git/编辑器改写了换行符 | 用 `python -c "print(open('data/train_final.jsonl','rb').read().count(b'\r'))"` 查，应为 0 |
| 预测脚本说"已存在，跳过" | 用了旧目录 | 换 `PRED_DIR=/root/autodl-tmp/preds_v3` 或先删旧文件 |
| 评测报连不上 MySQL | 本机 docker 的 MySQL 没起 | `docker start mysql`，确认 3307 端口 |
| 评测报 `LLM_API_KEY not found` | 没注入环境变量 | `run_eval_all.ps1` 会自动补占位值，若仍报错就在终端先 `$env:LLM_API_KEY='x'` |
