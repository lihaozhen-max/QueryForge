## 一、目标拆解：六项能力 → 具体可训练的行为

作业 3.2 列出六项能力。必须先把每项翻译成"模型输入什么、应该输出什么"，否则数据无从构造。

| 编号 | 作业要求的 ability | 落到本项目是什么行为 | 关键判分点 |
| --- | --- | --- | --- |
| 3.2.1 | 业务问题到字段映射 | 问句 → 选对 `fact_order.order_amount` 这类**表.字段** | 表字段选择正确、过滤条件符合业务含义 |
| 3.2.2 | 字段值识别与标准化 | 「iPhone」→ `dim_product.product_name = 'iPhone'`；「华东」→ `region_name='华东'` | 别名/口语 → 库内标准值；模糊值应澄清 |
| 3.2.3 | 指标口径理解与计算 | 「销售额」→ 按 `GMV` 口径 `SUM(fact_order.order_amount)`，而非 `COUNT(*)` | 聚合函数、分子分母、去重、时间口径 |
| 3.2.4 | 查询意图澄清 | 信息不全（缺时间/粒度/口径）时**先反问**，不硬猜 | 能否识别缺失条件、反问是否具体 |
| 3.2.5 | 多表关联与条件生成 | 正确走 `fact_order → dim_product / dim_region / dim_date` 的 `JOIN` 路径 | JOIN 路径、WHERE 是否遗漏、分组粒度 |
| 3.2.6 | SQL 安全与方言适配 | 只出 `SELECT`；MySQL 方言；拒绝 `DELETE/DROP/UPDATE` | 可执行、符合方言、只读 |

**当前基线（微调前）的真实水平 —— 这是选型的依据：**

| 能力 | 现有流水线是怎么做的 | 微调前的短板 |
| --- | --- | --- |
| 3.2.1 / 3.2.5 | 三路召回 + `filter_table` 收窄 + 主外键补全，`generate_sql` 拼长提示词 | 依赖召回质量；召回漏了就必错 |
| 3.2.2 | ES 全文检索字段真实取值，把命中值塞进字段 `examples` | 口语/别名不在库里时召回不到 |
| 3.2.3 | 把 `metric_infos`（GMV/AOV 口径）写进提示词 | 靠提示词约束，长上下文下易被稀释 |
| **3.2.4 澄清** | **完全没有实现** —— `validate_sql` 失败就 `correct_sql` 重写，从不反问 | **项目最大的能力缺口，也是微调收益最大的点** |
| 3.2.6 | 提示词里写"只能查询" | 纯提示词约束，无硬校验，无方言显式声明 |

> **选型结论**：3.2.4（澄清）是唯一"现有工程方案完全没覆盖"的能力，微调把它做出来，就是最硬的交付亮点。3.2.1/3.2.5 属于"提升召回容错"，3.2.2/3.2.3 属于"把提示词知识内化进权重"，3.2.6 属于"对齐输出格式与安全边界"。

## 二、评测集：程序化生成（无人工标注条件下的方案）

**没有人工标注**，因此不能靠人写标准答案。但也**不能"让大模型凭空编 SQL"** —— 编出来的 SQL 未必能执行、能执行也未必口径正确，等于用幻觉当标准答案，评测结论就失去意义。

**采用方案：模板抽样 + 数据库硬校验。**

```
conf/meta_config.yaml（表/字段/指标语义）
        +
dw.sql（真实 DDL + 真实维度取值）
        ↓
gen_eval_set.py  按六项能力套模板 → (中文问题, 标准 SQL / 澄清要点, capability)
        ↓
validate_sql.py  在 SQLite 影子库执行每条标准 SQL → 失败即报错，保证答案可执行
```

三条原则：

1. **答案必须可执行验证**。每条标准 SQL 都在由 `dw.sql` 真实数据构建的影子库上跑一遍，**跑不通就不算数**。这替代了人工核对中的"这条答案对不对"的一半工作。
2. **题目取自真实 schema 与真实取值**。品类/大区/省份/品牌/商品名都来自 `dw.sql` 的真实数据，不编造业务实体。
3. **澄清类样本的答案不是 SQL**，而是一组"必须澄清的要点"（缺时间范围 / 缺粒度 / 缺口径），评测时检查模型是否反问且覆盖要点。

### 如何划分训练/验证/测试（避免数据泄漏）

| 用途 | 来源 | 规模 |
| --- | --- | --- |
| **训练集** | 流水线批量产出 + 执行校验过滤 | 1000 |
| **验证集** | 从训练集同分布中留出 | 100 |
| **测试集** | **`gen_eval_set.py` 程序化生成，训练集完全不含** | 115（可扩到 150+） |

> 训练集与测试集**必须来自不同生成路径**：训练集是"流水线跑出来的 SQL"，测试集是"模板套出来的标准 SQL"。这样才不存在"用流水线自己的输出考自己"的退化。

### 一个重要约束：数据时间范围

`dim_date` 只覆盖 **2025-01-01 ~ 2025-03-31（Q1，90 天）**。因此：

- 「去年」在当前系统日期（2026-09）下指向 2025，**恰好落在数据范围内**；
- 但「2026 年」「去年下半年」「最近三个月」这类问题会**查空** —— 已在生成模板中避开；
- 若后续更改系统日期或扩数据，必须同步检查时间类问题的有效性。

## 三、数据方案

### 3.1 数据来源：三条腿

```
① 流水线批量产出（起量）       ② 人工抽检修正（保真）      ③ 负向/边界样本（补短板）
   run 现有 LangGraph           逐条核对字段与口径           澄清、拒答、方言、歧义
   ↓                            ↓                          ↓
   候选 (query, schema, sql)    修正为金标准                  手工编写
```

**① 流水线批量产出（你已选定的路线）**

复用现有代码，无需另写生成器：

- 入口：`app/services/query_service.py` 的 `QueryService.search()`，或直接 `compiled_graph.astream()`；
- 采集：开启 `stream_mode`，把节点的中间产物一并落盘 —— 这正好构成训练样本所需的**完整输入**：

| 训练需要的字段 | 从哪个节点/对象取 |
| --- | --- |
| `query` 用户问句 | `DataAgentState['query']` |
| 检索出的 schema | `merge_retrieved_info` 的返回值 `table_infos`（表 + 字段 + 类型 + role + examples + alias） |
| 指标定义与口径 | `merge_retrieved_info` 的 `metric_infos`（GMV/AOV 的 relevant_columns、alias） |
| 字段值样例 | `table_infos[*].columns[*].examples`（已由 ES 召回注入） |
| 时间上下文 / 方言 | `add_extra_context` 的 `date_info` / `db_info` |
| 标准 SQL | `generate_sql`（经 `validate_sql` 通过）或被 `correct_sql` 修好的最终版 |

> 实现建议：新增一个采集脚本，**不改动现有节点逻辑**，只在图外层订阅 `stream_mode="values"` 拿到每个节点的增量状态并落成 `jsonl`。这与项目现有架构（服务层复用 compiled_graph）一致，不引入新框架。

**② 人工抽检修正（这一步决定成败）**

- **抽检比例**：100% 过一遍**执行校验**，其中至少 30% 人工逐条核对口径与字段。
- **自动过滤**：只保留能通过 `validate_sql`（`EXPLAIN`）**且能成功执行**的样本 —— 现有 `DWMysqlRepository.validate_sql()` 可直接复用。
- **淘汰规则**：SQL 与问题语义不符、口径错误、字段选错的，**宁可丢弃也不要污染训练集**（错误标注比没有标注更有害）。
- **修正**：口径错的按 `meta_config.yaml` 的指标定义改；字段错的按真实 schema 改；**改完复跑一次执行校验**。

**③ 负向与边界样本（手工构造，不可省）**

现有流水线**产不出**这些样本，必须手写：

- **澄清样本**：`"看看销售情况"`（缺时间 + 缺粒度 + 缺口径）→ 期望输出反问；这是 3.2.4 的全部训练信号来源。
- **拒答样本**：`"把 dim_product 里下架的商品删掉"` → 期望拒绝并说明只能查询。
- **方言样本**：同一语义在 MySQL 下的写法（`LIMIT`、反引号、`DATE_FORMAT`），外加"不要用 `TOP`/`[]`"的反例。
- **歧义样本**：`"去年的销售额"` 若口径在 GMV / 实收间摇摆 → 应澄清。

### 3.2 数据规模（已确认）

| 用途 | 规模 | 来源 |
| --- | --- | --- |
| 训练集 | **1000** | 流水线批量产出 + 执行校验过滤 |
| 验证集 | 100 | 从训练集同分布中留出 |
| 测试集 | **115**（可扩至 150+） | `gen_eval_set.py` 程序化生成，已跑通 |

> **1000 条偏少，是本次方案最大的客观限制。** 应对方式：
> ① 严格控制 epoch（3 起步，不死磕）；② 优先保证**覆盖面**（六项能力都要有样本）而非单一能力的堆量；
> ③ 数据里必须包含负向样本（澄清 15–25%、拒答若干），否则 3.2.4/3.2.6 学不到。
> **经验**：1000 条干净且覆盖六项能力的数据，胜过 10000 条流水线原始产出。


### 3.3 数据格式（LLaMA-Factory 的 `sharegpt` / `alpaca`）

推荐 **`sharegpt`** 格式并保留系统提示词，因为需要区分"给 SQL"和"反问"两种输出：

```json
[
  {
    "conversations": [
      {
        "from": "system",
        "value": "你是掌柜问数的 SQL 生成助手。只依据给定的 schema 与指标口径生成一条 MySQL 只读查询；若信息不足（缺时间范围/统计粒度/指标口径），先提出反问，不要臆测。"
      },
      {
        "from": "human",
        "value": "【可用表结构】\n{tables_yaml}\n\n【指标口径】\n{metrics_yaml}\n\n【当前时间】\n{date_info}\n\n【数据库】\n{db_info}\n\n【用户问题】\n各个地区iPhone去年卖了多少钱"
      },
      { "from": "gpt", "value": "SELECT r.region_name, SUM(f.order_amount) AS gmv FROM fact_order f JOIN dim_product p ON f.product_id = p.product_id JOIN dim_region r ON f.region_id = r.region_id JOIN dim_date d ON f.date_id = d.date_id WHERE p.product_name LIKE '%iPhone%' AND d.year = 2025 GROUP BY r.region_name;" }
    ]
  },
  {
    "conversations": [
      { "from": "system", "value": "……同上的系统提示词……" },
      { "from": "human", "value": "【可用表结构】\n{tables_yaml}\n\n【用户问题】\n看看销售情况" },
      { "from": "gpt", "value": "这个问题还缺少几个关键信息，我需要确认后才能写查询：\n1. 统计的时间范围？（如 2025 年全年、最近 3 个月）\n2. 按什么维度看？（按地区 / 按品类 / 按月份）\n3. 看哪个指标？（GMV 成交总额 / AOV 平均客单价）" }
    ]
  }
]
```

**为什么要把 schema 放进 `human` 而不是 `system`**：schema 逐样本变化，属于"本次输入"；system 放固定行为约束（只读、澄清策略、方言）。这样微调后仍能与线上 `generate_sql.prompt` 的编排对接。

同步在 `dataset_info.json` 注册：

```json
{
  "zhangguiwenshu_sft": {
    "file_name": "zhangguiwenshu_sft.json",
    "formatting": "sharegpt",
    "columns": { "messages": "conversations" },
    "tags": {
      "role_tag": "from",
      "content_tag": "value",
      "user_tag": "human",
      "assistant_tag": "gpt",
      "system_tag": "system"
    }
  }
}
```

## 四、基座模型选型

### 4.1 结论：Qwen3-8B

**已确认使用 Qwen3-8B Instruct，不做 14B 及以上。** 理由：

- 8B 是这个任务在 1000 条数据规模下的**性价比最优点**：参数量足够支撑多表 `JOIN` 与结构化输出，单卡 QLoRA 就能完成；
- 数据量只有 1000 条时，更大的基座**更容易过拟合**，收益提升有限而成本翻倍；
- 中文与 SQL 能力均衡、LLaMA-Factory 模板完备、社区资料最多，出问题好排查。

**明确排除**（避免浪费预算）：

- ❌ ≤3B 超小模型：复杂 `JOIN` 与澄清策略学不稳；
- ❌ MoE 巨型模型（100B+）：1000 条数据撑不起，单次 LoRA 代价远超预算；
- ❌ 14B / 32B：在 100 元预算下与 8B 的收益差距不足以支撑额外成本。

### 4.2 可选加分项（预算允许再做）

若 8B 跑完后预算仍有余，可加做一组 **Qwen3-Coder** 对照（同数据、同超参），在冻结测试集上对比。
成本可控，能让交付从"我调了一个模型"升级为"我做了选型对比并给出数据结论"。**属加分项，非必做**。

### 4.3 显存与训练方式（8B 实际需求）

| 方式 | 显存需求（粗估） | 说明 |
| --- | --- | --- |
| LoRA (bf16) | ~24–32 GB | 单卡 4090 24G 偏紧，A100 40G 稳妥 |
| **QLoRA (4bit)** | **~12–16 GB** | **单卡 4090 24G 足够，推荐** |

> 建议直接用 **QLoRA (4bit)**：8B 模型在 1000 条数据上，QLoRA 与 LoRA 的最终效果差异很小，但显存占用减半、更省钱。

### 4.4 费用核算（上限 100 元）

按 1000 条样本、`cutoff_len=4096`、QLoRA、3 epoch 估算：

| 项目 | 估算 |
| --- | --- |
| 总步数 | 1000 ÷ 有效batch16 × 3 epoch ≈ **190 步** |
| 纯训练时长 | 约 **0.2–0.5 小时** |
| 加数据加载/评测/调试余量 | 实际占卡约 **1.5–3 小时** |
| 4090 级别时租 | 约 ¥1.5–3 / 小时 |
| **单次实验成本** | **约 ¥5–10** |
| **含冒烟 + 调参 + 对照的总计** | **约 ¥30–60，安全落在 100 元内** |

**省钱要点（重要）**：

1. **本机把数据、脚本、评测全部做完再租卡** —— 租卡只做"训练"一件事，不要按小时付费调试代码；
2. 先 `--max_samples 50` 冒烟确认不 OOM、loss 正常，再开全量；
3. 打开 `save_steps` 支持断点续训，中断不用重跑；
4. 训练完**立刻把 LoRA 权重下载回本机**再释放实例；
5. 评测尽量在本机做（连自己的 MySQL），不占卡。

**选平台建议**：优先 4090 / A100 40G 且**按小时计费、可随时释放**的平台；对比时看"同卡型时价 + 是否预装 PyTorch 镜像"（预装镜像能省 20–30 分钟环境配置，等于直接省钱）。

## 五、训练方案（LLaMA-Factory）

### 5.1 环境（离卡机器的准备 + 租卡机器）

- **本机（Windows，当前 `.venv`）**：只做**数据处理与评测**，不需要装 CUDA 版 torch。
- **租卡机器（Linux + NVIDIA）**：装 LLaMA-Factory，跑训练。

**版本要点（已核实）**：LLaMA-Factory 最新版为 **v0.9.5**，已支持 **Qwen3.5/3.6、GLM-4.7-Flash**，并要求 **Python ≥ 3.11**、兼容 **Transformers v5**。租卡时建议直接拉官方镜像，避免自己配环境：

```bash
git clone --depth 1 https://github.com/hiyouga/LLaMA-Factory.git
cd LLaMA-Factory
pip install -e ".[torch,metrics]"     # 或直接用官方 docker 镜像
llamafactory-cli version
```

> 参考：[LLaMA-Factory（GitHub）](https://github.com/hiyouga/LLaMA-Factory) · [中文文档](https://llamafactory.readthedocs.io/zh-cn/latest/)

### 5.2 训练配置（LoRA 起步，8B 为例）


### 5.3 执行

```bash

llamafactory-cli train train_qwen3_8b_lora.yaml --max_samples 50

# 正式训练
llamafactory-cli train train_qwen3_8b_lora.yaml

# 推理验证

# 导出合并后的模型（便于接到本项目做端到端评测）

```

### 5.4 调参优先级（按收益排序）

1. **数据质量与覆盖面** ← 收益最大，优先投入时间
2. **`cutoff_len`**：schema 被截断会直接毁掉 3.2.1/3.2.5，先确认不截断
3. `learning_rate`（1e-4 / 2e-4 两档对比）
4. `num_train_epochs`（2 / 3 / 4，警惕过拟合）
5. `lora_rank`（16 / 32 / 64）

## 六、评测方案

**只报"跑通了"是不够的，必须给出可量化的前后对比。**

### 6.1 三层指标

| 层级 | 指标 | 计算方式 | 对应能力 |
| --- | --- | --- | --- |
| L1 语法可用 | **可执行率** | 生成 SQL 能通过 `EXPLAIN` 的比例 | 3.2.6、3.2.5 |
| L2 执行正确 | **执行准确率（EX）** | 执行结果集与金标准**完全一致**的比例 | 3.2.1、3.2.2、3.2.3 |
| L3 行为正确 | **澄清/拒答准确率** | 该反问时反问、该拒答时拒答的比例 | 3.2.4、3.2.6 |

> **L2 为什么用"结果集比对"而不是"SQL 文本比对"**：同一个业务问题有多条等价 SQL（JOIN 顺序、别名、`WHERE` 位置），文本比对会误判。执行结果集比对（EX）是 Text2SQL 领域的标准做法，也更贴合"问数"的真实目标 —— 用户要的是数据，不是特定的 SQL 写法。

### 6.2 对比矩阵（交付材料核心）

| 配置 | 可执行率 | 执行准确率 EX | 澄清准确率 | 说明 |
| --- | --- | --- | --- | --- |
| 基线：DeepSeek API + 长提示词（现状） | | | 0% | 澄清能力为 0 |
| 基线：Qwen3-8B 原版 + 长提示词（未微调） | | | | 关键对照组：证明收益来自微调而非换模型 |
| **微调后：Qwen3-8B LoRA + 短提示词** | | | | 主结果 |
| 微调后：Qwen3-Coder LoRA + 短提示词 | | | | 基座选型对照 |

**消融实验（有余力再做）**：

- 去掉负向样本 → 看澄清/拒答准确率掉多少（证明负向样本的价值）
- 减少 schema 覆盖 → 看 3.2.5 掉多少
- 只训练 1 epoch vs 3 epoch → 看过拟合拐点

### 6.3 微调后的工程接入（澄清能力确定接入）

微调模型最终**替换 `app/agent/nodes/generate_sql.py` 里的 `llm`**，并保留现有编排：

- 微调模型承担 **`generate_sql`**（生成 SQL）与 **`correct_sql`**（按报错重写）两个节点；
- **新增澄清分支（已确认接入）**：在 `add_extra_context` 之后、`generate_sql` 之前插入一个
  **信息充分性判断节点**，让微调模型先判断问题是否具备「时间范围 / 统计粒度 / 指标口径」；
  信息不足则**直接结束并返回反问**，不进入 SQL 生成；信息充分才继续。
  实现上沿用现有模式：新增 `app/agent/nodes/check_sufficiency.py` + 在 `graph.py` 加一条条件边，
  与现有 `validate_sql` 的条件边写法一致，不引入新框架。
- 复用现有 `validate_sql`（`EXPLAIN`）做 L1 校验 —— **微调不替代校验，二者叠加**。

> 保留 `EXPLAIN` 校验环是这套方案的优势：即使微调模型偶发幻觉，也有一层数据库级兜底。
> 澄清分支的价值在于**在浪费一次 SQL 生成和一次数据库往返之前就把问题问清楚**。

## 八、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **训练数据来自有缺陷的流水线** → 模型只学会模仿它的错误 | 效果提升有限甚至学到坏习惯 | ① 测试集走模板生成、与训练集不同路径（已实现）；② 训练样本 100% 过执行校验；③ 宁可丢样本不污染 |
| **标准答案本身写错**（如字段名拼错） | 评测全部误判，结论作废 | 已有 `finetune/validate_sql.py` 在影子库上逐条执行校验；生成器改动后必须重跑 |
| **schema 被 `cutoff_len` 截断** | 3.2.1 / 3.2.5 直接崩 | `cutoff_len=4096` 起步；先统计样本长度分布确认不截断 |
| **过拟合**（1000 条数据量偏小） | 训练 loss 降但评测不涨 | 3 epoch 起了就停；用验证集选最优 checkpoint；**不要盲目加 epoch** |
| **澄清样本比例失衡** → 模型"动不动就反问" | 正常问题也被反问 | 澄清样本占 15–25%（当前测试集 18/115 ≈ 15.7%）；测试集同时含"该给 SQL"和"该反问"两类 |
| **租卡成本超 100 元** | 预算超支 | 本机做完数据与评测再租卡；先 50 条冒烟；`save_steps` 支持续训；训完立刻下载权重并释放 |
| **模型输出与项目方言/表名不一致** | 端到端接不上 | 训练数据直接用 `meta_config.yaml` 的真实表名字段名；system 提示词固定"MySQL 只读" |
| **数据时间范围只有 Q1** | 时间类问题查空 | 生成器已避开超范围表述；改系统日期或扩数据后必须复查 |

| **本机 Windows 无法训练** | 阻塞 | 本机只做数据与评测；训练全在租卡机器，避免在 8GB 本机硬撑 |
