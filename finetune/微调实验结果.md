## 二、评测设计

### 三层指标

| 层级 | 指标 | 含义 |
| --- | --- | --- |
| L1 | 可执行率 | 生成的 SQL 能通过 `EXPLAIN` + 实际执行 |
| L2 | **执行准确率（EX）** | SQL 跑出的**结果集**与标准答案一致 |
| L3 | 澄清/拒答准确率 | 该反问时反问、该拒绝时拒绝 |

> **为什么用结果集比对而不是 SQL 文本比对**：同一业务问题有多条等价 SQL
> （JOIN 顺序、别名、WHERE 位置不同），文本比对会误判。用户要的是数据，
> 不是某种特定写法。

### 评测集

115 条，全部由模板 + 真实数据库取值生成，标准 SQL 均经执行校验：

| 能力 | 条数 |
| --- | --- |
| 3.2.1 业务问题到字段映射 | 7 |
| 3.2.2 字段值识别与标准化 | 24 |
| 3.2.3 指标口径理解与计算 | 14 |
| 3.2.4 查询意图澄清 | 18 |
| 3.2.5 多表关联与查询条件生成 | 47 |
| 3.2.6 SQL 安全与方言适配 | 5 |
| **合计** | **115**（93 条 SQL + 22 条澄清/拒答） |

### 关键设计：只变一个变量

两个 Qwen3 模型（原版 / 微调后）使用**完全相同的检索上下文**和相同题目，
检索链路、schema 内容、system 提示词全部一致 —— 唯一的差异是"有没有微调"。

为做到这一点，预测时**跳过流水线里的两个 LLM 过滤节点**，直接用召回结果作为
schema 上下文（详见 `dump_context.py` 的说明）。原因是过滤节点有时会裁掉 JOIN
需要的维表，会让"模型答错"与"过滤裁错"两个变量混在一起。

## 三、主要结果

### 3.1 对比矩阵

| 配置 | L1 可执行率 | **L2 执行准确率 EX** | L3 澄清/拒答 |
| --- | --- | --- | --- |
| 基线：现有流水线 + deepseek-flash | 98.9% | 81.7% | **0.0%** |
| 基线：Qwen3-8B **原版**（未微调） | 84.9% | 61.3% | 59.1% |
| **微调后：Qwen3-8B LoRA** | **95.7%** | **80.6%** | 45.5% |

> ⚠️ 口径说明：deepseek 基线是**带 LLM 过滤**跑的，两个 Qwen3 是**不过滤**跑的。
> 因此 deepseek 那行的数字不可与 Qwen3 两行直接逐位对比；但
> **原版 vs 微调后**这两行是同口径的，差值才是可靠的微调收益。

### 3.2 微调的净收益（原版 → 微调后，同口径）

| 指标 | 原版 | 微调后 | 变化 |
| --- | --- | --- | --- |
| L1 可执行率 | 84.9% | 95.7% | **+10.8** ✅ |
| **L2 执行准确率 EX** | 61.3% | **80.6%** | **+19.3** ✅✅ |
| L3 澄清/拒答 | 59.1% | 45.5% | **−13.6** ❌ |

### 3.3 按能力分层（原版 → 微调后）

| 作业能力 | 条数 | EX 原版 | EX 微调后 | 变化 |
| --- | --- | --- | --- | --- |
| 3.2.1 字段映射 | 7 | 71.4% | 71.4% | 持平 |
| **3.2.2 字段值标准化** | 24 | 66.7% | **79.2%** | **+12.5** |
| **3.2.3 指标口径** | 14 | 57.1% | **85.7%** | **+28.6** 🔥 |
| 3.2.5 多表关联 | 47 | 57.4% | **80.9%** | **+23.5** 🔥 |
| 3.2.6 安全与方言 | 5 | 100% | 100% | 持平 |

**改善最显著的是 3.2.3 指标口径（+28.6）和 3.2.5 多表关联（+23.5）** ——
这两项正是微调要解决的核心问题：按 GMV/AOV 的正确口径做聚合、走对 JOIN 路径。

### 3.4 L3 拆开看：澄清与拒答走向相反

| | 澄清类（该反问） | 拒答类（该拒绝） |
| --- | --- | --- |
| 原版 | **72%**（13/18） | 0%（0/4） |
| 微调后 | **39%**（7/18） | **75%**（3/4） |

预测输出的类型分布也印证了这个趋势：

| 配置 | 生成 SQL | 澄清/拒答 |
| --- | --- | --- |
| deepseek 流水线 | 114 | 1 |
| Qwen3-8B 原版 | 86 | 29 |
| Qwen3-8B LoRA | **105** | 10 |

## 四、结果分析

### 4.1 微调显著提升了 SQL 生成能力

EX 从 61.3% 提升到 80.6%（**+19.3 个百分点**），且可执行率从 84.9% 升到 95.7%。
说明模型确实学会了本项目的表结构、字段语义与指标口径，而不只是"格式变好"。

尤其在**指标口径（+28.6）**上：原版模型经常把"平均客单价"写成 `SUM`、
把"销售额"用错聚合函数；微调后能正确遵循 GMV / AOV 的口径定义。

**横向对比**：8B 的 LoRA 模型达到 80.6%，逼近云端 deepseek 的 81.7%，
但它是**可自己部署的 8B 小模型**，不按调用次数付费 —— 这正是微调的价值。

### 4.2 L3 澄清能力出现回退（负面结果，如实记录）

微调后**澄清类准确率从 72% 降到 39%**，但同时**拒答类从 0% 升到 75%**。

**原因分析**：

1. **数据配比失衡**。训练集里 SQL 类样本 424 条，澄清类仅 **33 条**（占 4.9%）。
   微调后模型明显更倾向"给出 SQL"（生成 SQL 的条数从 86 升到 105），
   把本该反问的问题也硬答了。
2. **两类任务的难度不同**。拒答的特征非常显式（"删掉""改成 0"等危险动词），
   且话术模板统一，33 条就足以学会；而"什么时候该反问"需要判断**信息是否充分**，
   是更微妙的决策，样本不足时学不到。
3. **上下文更完整反而降低了反问动机**。评测时给的是**不过滤**的较完整 schema，
   模型倾向于认为"信息已经够了我能写 SQL"，进一步压低了反问率。

**这是本次实验的负面结果，但它有明确的数据原因，不是随机波动。**

### 4.3 为什么 deepseek 基线的 L3 是 0%

现有流水线**没有澄清分支**（LangGraph 里没有"信息充分性判断"节点），
遇到信息不全的问题也会硬编 SQL。实测 22 条澄清/拒答样本中，它生成了 114 条 SQL、
只有 1 条非 SQL 输出 —— 即几乎从不反问、从不拒绝。

这印证了规划文档的判断：**3.2.4 澄清是现有工程的完全空白**。

## 五、结论

| 结论 | 依据 |
| --- | --- |
| ✅ 微调显著提升 SQL 生成能力 | EX +19.3，可执行率 +10.8 |
| ✅ 指标口径与多表关联改善最大 | +28.6 / +23.5 |
| ✅ 学会了拒绝危险请求 | 拒答 0% → 75% |
| ✅ 8B 小模型接近云端大模型水平 | 80.6% vs 81.7%，但可自部署 |
| ❌ 澄清能力回退 | 72% → 39%，主因澄清样本仅 33 条 |
| ✅ 未过拟合 | eval_loss 0.0933 < train_loss 0.2221 |

**总体判断：微调成功。** 核心指标（EX）大幅提升且无过拟合；
唯一回退的 L3 澄清项有明确的数据原因，属于"可改进项"而非"方法失败"。

## 六、后续改进方向

| 方向 | 做法 | 预期 |
| --- | --- | --- |
| **扩充澄清样本** | 从 33 条补到 100+ 条（可继续用反向变换合成），重新训练 | 有望把 L3 澄清拉回并超过原版 |
| 调整类别配比 | 提高澄清样本在训练集中的占比 | 让模型更愿意反问 |
| 改用 `qwen3_nothink` 模板 | 训练时用含思维链的 `qwen3` 模板，但训练答案是纯 SQL，存在不一致 | 可能小幅提升 L2 |
| 加入真实用户提问日志 | 反向变换受限于源 SQL 的要素，真实日志覆盖更广 | 澄清样本更自然多样 |
| 接入主流程（P6） | 把微调模型替换 `generate_sql` 节点，并新增澄清分支 | 端到端验证 |

## 七、复现方式

```bash
# 1) 准备评测集与训练数据（本机）
python finetune/gen_eval_set.py && python finetune/validate_sql.py
python finetune/make_corpus.py
python finetune/synthesize_train_data.py --target 500 --concurrency 8
python finetune/build_correct_sql_data.py
python finetune/make_negatives.py
python finetune/build_final_train_set.py

# 2) 训练（租卡机器）
llamafactory-cli train train_qwen3_8b_lora.yaml
llamafactory-cli export export_qwen3_8b.yaml

# 3) 预测（租卡机器）
python finetune/dump_context.py            # 本机导出上下文
python predict_with_model.py --model .../Qwen3-8B         --out preds/base.jsonl
python predict_with_model.py --model .../qwen3-8b-merged  --out preds/lora.jsonl

# 4) 评测（本机）
python finetune/eval_ex.py --db mysql --predictions preds/base.jsonl
python finetune/eval_ex.py --db mysql --predictions preds/lora.jsonl
```
