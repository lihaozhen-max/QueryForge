# 微调实验结果

> 本文档记录 Qwen3-8B 微调的**实测结果**与**分析**，包含**两轮实验**：
>
> * **第一轮**：在 v1 数据（656 条）上做训练轮数消融 → 发现澄清能力回退
> * **第二轮**：换成 v2 数据（1591 条）只训 1 epoch → **L2 大涨，但澄清假设被证伪**
>
> 方案设计见 `微调规划.md`，实操流程见 `微调流程详解.md`，
> 第二轮照抄步骤见 `第二轮重训说明.md`。
>
> **本文所有数字均为本机真实 MySQL（`dw` 库）跑出来的实测值**，不是估算。

---

## 〇、结论速览（只看这一段也够）

| 配置 | L1 可执行率 | **L2 执行准确率 EX** | L3 澄清/拒答 |
| --- | --- | --- | --- |
| P 现有流水线 + deepseek-flash（云端） | 98.9% | 81.7% | **0.0%** |
| A Qwen3-8B 原版（未微调） | 83.9% | 61.3% | **77.3%** |
| B 第一轮 LoRA 1 epoch（v1 数据 656 条） | 93.5% | 79.6% | 59.1% |
| **B′ 第二轮 LoRA 1 epoch（v2 数据 1591 条）** | **100.0%** | **87.1%** | 50.0% |

**三句话结论**：

1. ✅ **微调成功，交付 B′**。EX 从 61.3% 提到 **87.1%（+25.8）**，
   可执行率 **100%** —— 已经超过云端 deepseek 基线的 81.7%，而且是可自部署的 8B 小模型。
2. ❌ **"用无实体超短问句训练就能学会澄清"这个假设被证伪**。
   L3 不升反降（59.1% → 50.0%），逐条看是"改好 1 条、改坏 3 条"。
   **澄清能力不该靠继续训模型解决，应从工程侧加确定性前置判断。**
3. ⚠️ **eval_loss 更低 ≠ 业务指标更好**。第二轮 eval_loss 从 0.0874 降到 0.0723，
   但那只是数据变了；而第一轮内部 2/3 epoch 的 loss 更低、EX 反而掉 3.3 个点。

## 一、实验设置

### 1.1 对照组与实验组

| 编号 | 配置 | 说明 |
| --- | --- | --- |
| **P** | 现有流水线 + deepseek-flash（云端） | 现状基线，代表"一分钱不花能拿到的水平" |
| **A** | Qwen3-8B **原版**，未微调 | 微调的起点，与 B/B′ **同口径** |
| **B** | Qwen3-8B + LoRA，**1 epoch**（v1 数据） | 第一轮最优档 |
| B2 / B3 | Qwen3-8B + LoRA，2 / 3 epoch（v1 数据） | 第一轮轮数消融 |
| **B′** | Qwen3-8B + LoRA，**1 epoch**（v2 数据） | **第二轮，最终交付** |

> **口径说明**：P 是**带 LLM 过滤节点**跑的，与其余各行口径不同，**不可逐位对比**。
> A / B / B2 / B3 / B′ 使用**完全相同的检索上下文与 system 提示词**，
> 唯一差异是模型权重与训练数据，**彼此可直接对比**。

| 学习率 / 调度 | 1e-4 / cosine，warmup 0.1 |
| 等效 batch size | 16（per_device 2 × 梯度累积 8） |

评测集 `test.jsonl` 全程**不参与**训练样本生成。

### 1.4 训练曲线

| 实验 | **eval_loss** | 说明 |
| --- | --- | --- |
| v1 / 1 epoch | 0.0874 | 第一轮最优档（EX 最高） |
| v1 / 2 epoch | 0.0577 | loss 更低，**EX 反而掉 3.3 个点** |
| v1 / 3 epoch | 0.0537 | loss 最低，**EX 仍不如 1 epoch** |
| **v2 / 1 epoch** | **0.0723** | 验证集不同（138 条），**不可与上三行比 loss** |

> ⚠️ **本表最重要的一行信息是"不可比"**：v1 与 v2 的验证集不是同一份，
> loss 数值没有可比性。而 v1 内部三组同数据同验证集，
> **loss 单调下降、EX 却 1 epoch 最优** —— 这才是可靠信号：
> **选模型必须看下游业务指标（EX），不能只看 loss。**

## 二、评测设计

### 2.1 三层指标

| 层级 | 指标 | 含义 |
| --- | --- | --- |
| L1 | 可执行率 | 生成的 SQL 能通过 `EXPLAIN` 校验并实际执行成功 |
| L2 | **执行准确率（EX）** | SQL 跑出的**结果集**与标准答案一致（不是比 SQL 文本） |
| L3 | 澄清/拒答准确率 | 该反问时反问、该拒绝时拒绝 |

> **为什么比结果集而不是比 SQL 文本**：同一业务问题有多条等价 SQL
> （JOIN 顺序、别名、WHERE 位置不同），文本比对会把正确答案判错。
> 用户要的是数据，不是某种特定写法。

### 2.2 评测集（115 条，全程冻结）

全部由模板 + 真实数据库取值生成，93 条标准 SQL 均经真实 MySQL 执行校验：

| 能力 | 条数 | 其中 SQL 类 |
| --- | --- | --- |
| 3.2.1 业务问题到字段映射 | 7 | 7 |
| 3.2.2 字段值识别与标准化 | 24 | 24 |
| 3.2.3 指标口径理解与计算 | 14 | 14 |
| 3.2.4 查询意图澄清 | 18 | 0（全部应反问） |
| 3.2.5 多表关联与查询条件生成 | 47 | 47 |
| 3.2.6 SQL 安全与方言适配 | 5 | 1（另 4 条为危险请求，应拒答） |
| **合计** | **115** | **93 SQL + 22 澄清/拒答** |

### 2.3 关键设计：只变一个变量

A / B / B2 / B3 / B′ 使用**完全相同的检索上下文**和相同题目 ——
检索链路、schema 内容、system 提示词全部一致，**唯一差异是模型权重（及训练数据）**。

为做到这一点，预测时**跳过流水线里的两个 LLM 过滤节点**，直接用召回结果
作为 schema 上下文（见 `dump_context.py`）。原因：过滤节点有时会裁掉 JOIN
需要的维表，会让"模型答错"和"过滤裁错"两个变量混在一起。

### 2.4 评测噪声是零（已实测）

为确认小差异不是随机波动，**同一个原版模型在两次不同运行中各预测了一遍**：

| | L1 | L2 | L3 |
| --- | --- | --- | --- |
| 第一次 | 84.9% | 61.3% | 77.3% |
| 第二次 | 83.9% | 61.3% | 77.3% |

115 条里有 13 条**输出文字不同**（`do_sample=False` 下仍有少量非确定性），
但**判定结果全部相同**，三层指标差异 ≤ 1 条。

> **结论：本评测的噪声底约为 1 条 / 93 条（≈1 个百分点）**，
> 因此 ≥2 条的差异可以当作真实变化来解读。
> 这条基准让后面的"改好 1 条、改坏 3 条"能够被严肃对待。

### 2.5 评测器的两处修正（只影响 L3，L1/L2 未变）

1. **拒答关键词表过窄**：初版只有"无法执行 / 只能生成只读 / 抱歉"等少数写法，
   把**语义完全正确但措辞不同**的拒绝判成失败 —— 例如原版模型回答
   "生成的 SQL 只能用于查询，**不能涉及数据写入、更新、删除**等操作"，一个词都没命中。
   已扩充等价说法，并新增 `_contains_sql_block()` **伪拒绝检测**
   （嘴上拒绝、正文却贴出 SQL 代码块的仍判失败，实测抓到 1 条
   "拒答 + 附带 `DELETE FROM fact_order;`"的样本）。
   修正后基线 L3 由 59.1% 升到 **77.3%**。
2. **澄清/拒答类训练样本与评测集查重**：发现一处真实泄漏（见 4.3），
   修复后两类样本重合数为 **0**。

### 3.2 第一轮：训练轮数消融（同数据同验证集）

| 指标 | A 原版 | B（1 ep） | B2（2 ep） | B3（3 ep） | 最优 |
| --- | --- | --- | --- | --- | --- |
| L1 可执行率 | 84.9% | **93.5%** | 91.4% | 92.5% | **1 ep** |

**1 epoch 最优，且 loss 越低 EX 越差。**

猜测原因：数据里 212 条（32%）是"错误 SQL → 修正 SQL"的纠错样本，
模式高度重复、损失上极易拟合。训到 2、3 轮后模型开始过度模仿纠错话术，
对字段/表选择的注意力被稀释。1 epoch 恰好停在泛化最好的位置。

> 这条结论也意味着**"多训几轮总没坏处"是错的**。

## 四、结果分析

### 4.1 L2 大涨是真实的，且来源可解释

v2 的 EX 达到 **87.1%**，比 v1 高 7.5 个点，比原版高 25.8 个点，
**已超过云端 deepseek 基线的 81.7%**。

**但要注意归因**：这一轮同时改了两件事，而证据指向 **JSON bug 修复是主因**：

| 改动 | 证据 |
| --- | --- |
| schema examples 修复 | 3.2.2 字段值标准化 **79.2% → 100.0%**，正是该能力的直接受益面 |
| 合成数据 394 → 948 条 | 覆盖面变大，MULTI_TABLE_JOIN 76.6% → 80.9% |
| 澄清样本改版 | **反向证据**：同一轮里澄清反而变差，说明它不是 L2 提升的来源 |

> ⚠️ **诚实的限制**：这两项改动没有做隔离实验（要再训两次、约 40 分钟）。
> 所以"JSON 修复贡献了多少"是**推断，不是实测**。

### 4.2 修掉的那个 JSON bug（本轮最有价值的发现）

`synthesize_train_data.py` 用**裸 SQL** 查询 `column_info`，而
`examples` / `alias` 在 MySQL 里是 **JSON 类型**：

* 走 ORM（`merge_retrieved_info` 的线上路径）→ SQLAlchemy 反序列化成 list ✅
* 走**裸 SQL** → 驱动把 JSON 列当字符串返回，
  `list(r.examples or [])` **把字符串按字符拆开**：

```
["C001", "C002"]  →  ['[', '"', 'C', '0', '0', '1', '"', ',', ' ', ...]
```

**第一轮 `train_synth.jsonl` 里 4880 个字段的 examples/alias 全是这种垃圾。**

后果是**训练/推理分布不一致**：训练时 schema 里的示例是乱码，
推理时（走 ORM）却是干净的 `C001`/`李伟`。模型要自己猜"这一串字符是什么"。

修复方式：加 `_as_list()` 显式再 `json.loads` 一次
（**字符串绝不能被 `list()` 或迭代**），并趁修复重新生成合成数据
（顺带从 394 条扩到 948 条 —— 第一轮被 `--target 500` 限量了）。

> **教训：同一个数据库列，走 ORM 和走裸 SQL 拿到的 Python 类型可能不一样。**
> 凡是 JSON / ARRAY 这类列，裸 SQL 查询后必须显式反序列化。
>
> **另一层教训**：这个 bug 让第一轮 79.6% 的成绩其实是"带着缺陷拿到的"。
> 如果不重新生成数据，它会一直藏着 —— 因为**训练不会报错，loss 也照常下降**。

### 4.3 澄清假设被证伪（本轮最重要的负面结果）

**我的假设**：第一轮 L3 回退的原因是训练集的澄清问句几乎每条都带业务实体
（"三星最近如何？"平均 9.9 字），而评测集 18 条应澄清题里 17 条**完全没有实体**
（"客单价怎么样"平均 6.6 字）。所以模型学成了"看到实体词就反问"，
而不是"信息不足就反问"。

**于是第二轮专门造了 238 条无实体超短问句**（平均 5.6 字、95% 无实体、覆盖 14 种缺失组合），
把澄清占比从 10.8% 提到 15.0%。

**结果：L3 从 59.1% 掉到 50.0%。假设不成立。**

逐条看（18 条应澄清题，v1 → v2）：

| 变化 | 条数 | 例子 |
| --- | --- | --- |
| ❌ 原本答错 → 仍然答错 | 4 | `客单价怎么样`、`利润率是多少`、`哪个卖得最好`、`按地区看一下` |
| ❌ **原本答对 → 变答错** | **3** | `销售怎么样？`、`最近一段时间销售额多少`、`最近生意好不好` |
| ✅ 原本答错 → 变答对 | **1** | `销售额是多少` |
| （两轮都答对） | 10 | — |

**净效果 −2 条。**

**关键证据：那 4 条"仍然答错"的题，在 v2 训练集里都有对应的样本。**
比如 `客单价怎么样` 和 `利润率是多少` 这两句几乎原样出现在了训练数据里，
模型**照样直接写 SQL**。这说明问题不是"没见过这种问法"，
而是 8B 模型**没有学会"判断信息是否充分"这个推理步骤** ——
它学到的是"这些问题长什么样"，而不是"什么情况下不该答"。

**同时发生的反效果**：模型整体变得更敢写 SQL（误给 SQL 从 5 条增到 8 条）。
加了 167 条澄清样本，反而让它更倾向于答 ——
很可能因为 SQL 类样本同时从 424 涨到 881 条，
而 SQL 能力在损失上的收益远大于"学会闭嘴"。

> **结论：堆澄清样本这条路走不通。** 继续加占比只会进一步压低 L2。
> 澄清应当从**工程侧**解决（见第六章）。

### 4.4 为什么 deepseek 基线的 L3 是 0%

现有流水线**没有澄清分支**（LangGraph 里没有"信息充分性判断"节点），
遇到信息不全的问题也硬编 SQL。实测 22 条澄清/拒答样本中，它只输出 1 条非 SQL，
即**几乎从不反问、从不拒绝**。

这印证了规划文档的判断：**3.2.4 澄清是现有工程的完全空白**。

### 4.5 评测噪声已量（方法学）

见 2.4：同一模型两次运行，三层指标差异 ≤ 1 条。
所以本文中 ≥2 条的差异（例如 L3 的 −2 条）都可以当作真实变化。

> 这也解释了为什么 `base` 的 L1 在两次运行里是 84.9% 和 83.9% —— 差 1 条，属噪声。

## 五、结论

| 结论 | 依据 |
| --- | --- |
| ✅ **微调成功，交付 B′（v2 数据 1 epoch）** | EX **+25.8**、可执行率 **100%** |
| ✅ **EX 87.1% 超过云端 deepseek 基线 81.7%** | 且是可自部署的 8B 小模型 |
| ✅ **字段值标准化做到满分** | 3.2.2 66.7% → **100.0%** |
| ✅ **修掉了一个一直藏着的训练数据 bug** | schema examples 4880 个字段全是单字符垃圾 |
| ✅ **1 epoch 最优；loss 更低 ≠ 指标更好** | 2/3 epoch 的 eval_loss 更低、EX 反而掉 3.3 |
| ❌ **"无实体短问句能教会澄清"被证伪** | L3 59.1% → 50.0%，改好 1 条、改坏 3 条 |
| ❌ **继续堆澄清样本是死路** | 澄清占比翻倍无效，且更压 L2 |
| ⚠️ **L2 提升的归因是推断，非隔离实验** | JSON 修复与数据扩容未拆开验证 |
| ⚠️ **拒答能力不稳定** | v1/v2 各错 1 条，且不是同一条 |

**总体判断：模型侧的工作到此为止。**
L2 已经足够好（87.1%，超过云端基线），继续在模型上投入的边际收益很低；
剩下的短板（澄清）应该用工程手段解决。

## 六、下一步：澄清从工程侧解决

**不要再用训练来解决澄清。** 理由是实测的：两轮数据专门优化过，L3 反而从 77.3%（原版）
一路降到 50.0%。而原版模型本身有 72.2% 的澄清能力 —— **它本来就会反问，是微调把它压掉了**。

### 建议方案：在 LangGraph 里加一个确定性前置判断节点

```
用户问题
   ↓
【新增】信息充分性判断（纯规则，不调模型）
   ├─ 有明确时间范围？   没有 → 反问"统计哪个时间段？"
   ├─ 有明确指标？       没有 → 反问"看哪个指标？"
   └─ 有明确分组维度？   没有 → 反问"按什么维度看？"
   ↓ 三项齐全
generate_sql（用微调后的 B′ 模型）
```

**为什么这比训模型好：**

| | 训模型 | 规则前置判断 |
| --- | --- | --- |
| 准确率 | 50%（实测） | **100%**（逻辑确定） |
| 可解释 | 不能 | **能**，每条追问都能说出缺什么 |
| 可测试 | 需要重训才知道 | **单元测试即可** |
| 代价 | 每轮 20–30 分钟 GPU | 本机开发，0 GPU |

而且这正好补上 4.4 指出的空白 —— **deepseek 基线 L3 = 0.0% 就是因为缺这个节点**。

### 其它可做项（优先级更低）

| 方向 | 说明 |
| --- | --- |
| 隔离实验 | 把"JSON 修复"和"数据扩容"拆开各训一次，确认归因（2×20 分钟） |
| 轮数复核 | v2 数据下最佳轮数未验证（只跑了 1 epoch）；`EPOCHS="1 2 3"` 可补 |
| 样本量 | 1591 条对 8B 模型偏少，可扩到 3–5k；但需先确认瓶颈在数据还是模型 |
| 真实提问日志 | 现在的评测集与语料同源，真实日志能暴露模板覆盖不到的问法 |
