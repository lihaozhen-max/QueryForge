### 1. 区别问数项目与智库项目

**一句话结论**：两者都是 RAG，但**掌柜智库是 Doc RAG**（检索文档片段，让大模型总结出答案），**掌柜问数是 DB RAG / NL2SQL**（检索数据库的元数据，让大模型生成 SQL，真正的答案由数据库执行 SQL 得到）。

**对比表**

| 对比项 | 掌柜智库（Doc RAG） | 掌柜问数（DB RAG / NL2SQL） |
| --- | --- | --- |
| 知识源 | 非结构化文档：PDF、Word、网页、FAQ | 结构化数据仓库：表、字段、指标、字段取值 |
| 索引对象 | 文档切分后的 chunk 文本向量 | **元数据**：字段信息 / 指标信息（向量索引）、字段取值（全文索引） |
| 检索结果 | Top-K 相关文本片段 | 相关的表、字段、指标定义、字段取值 |
| 大模型角色 | 阅读片段 → **直接写答案** | 阅读元数据 → **写 SQL**（不接触明细数据） |
| 最终答案来源 | 大模型生成的自然语言 | **数据库执行 SQL 返回的结果集** |
| 输出形态 | 一段话 / 一段总结 | 结构化数据，可渲染成表格、图表 |
| 正确性保障 | 难以自动校验，易出现幻觉 | SQL 可用 `EXPLAIN` 校验语法、失败可回环校正，数字由数据库计算，不会被"编造" |
| 典型失败 | 答非所问、引用错误 | 表/字段召回不全、SQL 语义错误 |

**核心差异展开**

1. **知识形态不同**：文档是"文字"，数仓是"表结构 + 数据"。数仓中的原始数据（几百万行明细）不可能全部塞进提示词，所以问数索引的不是数据本身，而是**描述数据的数据（元数据）**：表名、表描述、字段名、字段类型、字段角色、字段别名、字段取值样例、指标口径。
2. **大模型的定位不同**：智库让大模型"回答问题"；问数让大模型"翻译问题"——把自然语言翻译成 SQL。计算、聚合、排序全部交给数据库，从根本上规避了大模型算数不准、编造数字的问题。
3. **可校验性不同**：问数有一条智库没有的闭环——生成 SQL 后先用 `EXPLAIN` 校验，报错就把错误信息回灌给大模型重新生成（`validate_sql → correct_sql`），这是"可自愈"的 RAG。
4. **对用户的价值**：让不会写 SQL 的业务/运营人员，用一句"华北地区去年 iPhone 卖了多少钱"就能直接拿到数据，降低数据分析门槛。

### 2. 区别数据仓库与业务数据库？

**一句话结论**：业务数据库（OLTP）面向**前台用户的实时增删改查**，数据仓库（OLAP）面向**后台人员的历史数据分析**；前者要的是"快而准的单条事务"，后者要的是"大批量数据的统计聚合"。

**对比表**

| 对比项 | 业务数据库（业务仓库 / OLTP） | 数据仓库（数仓 / OLAP） |
| --- | --- | --- |
| 面向对象 | 前台用户（下单、支付、注册） | 后台分析人员、BI、决策层 |
| 典型操作 | 高频 INSERT / UPDATE / DELETE / 单条 SELECT | 低频大批量 SELECT，一般**只增不改不删** |
| 数据内容 | 当前**最新状态**的数据 | 业务库同步过来的**历史全量数据**（保留快照） |
| 数据更新方式 | 用户操作时**实时**变更 | 定时（每天/每小时）通过 ETL 抽取增量后加载 |
| 建模方式 | 范式化（3NF），尽量减少冗余 | 反范式，**星型/雪花模型**，为查询方便适当冗余 |
| 数据量级 | 相对小（只存活跃数据） | 极大（累积多年历史） |
| 优化目标 | 事务、并发、响应时间（毫秒） | 吞吐、扫描效率、聚合性能（秒~分钟） |
| 典型 SQL | `select * from orders where id=?` | `select 地区, sum(金额) ... group by 地区` |

**为什么问数要对着数仓做，而不是业务库**

1. 分析型 SQL 通常要扫描大量数据，直接打在业务库上会**拖垮线上业务**。
2. 数仓已经做过清洗、汇总、维度建模，字段有清晰的业务语义（哪些是维度、哪些是度量），**更适合让大模型理解**。
3. 数仓保留历史数据，才能回答"去年"、"同比"、"环比"这类分析问题。

**本项目的 dw 库（经典星型模型）**

- 事实表（fact_，中心，存度量值）：`fact_order`（订单数量 `order_quantity`、订单金额 `order_amount`，以及 4 个外键）
- 维度表（dim_，四周，存分析角度）：`dim_customer`、`dim_product`、`dim_date`、`dim_region`
- 事实表**用于聚合**（sum/avg/count），维度表**用于分组和过滤**（group by / where）。

### 3. 说说问数项目的 2 个阶段

问数本质是一次 **DB RAG**，和所有 RAG 一样分为**索引**和**检索**两个阶段，两个阶段在项目里是**两个独立入口**。

#### 阶段一：索引（离线，跑一次，入口 `app/scripts/build_meta_knowledge.py`）

目标：把数仓的元数据整理进"元数据知识库"，并建立多种可被召回的索引。

1. 从配置文件 `conf/meta_config.yaml`（人工补充的表/字段/指标描述、别名）+ 数仓 dw 库（自动采集字段类型、字段取值）汇总元数据；
2. **结构化存储**：写入 MySQL 的 `meta` 库四张表 —— `table_info`、`column_info`、`metric_info`、`column_metric`；
3. **向量索引**：把**字段信息**和**指标信息**（名称 / 描述 / 每个别名）向量化后写入 Qdrant，用于**语义召回**；
4. **全文索引**：把**维度字段的取值**（如"华北"、"iPhone 15"）写入 Elasticsearch，用于**字面召回**。

> 运行方式：`python -m app.scripts.build_meta_knowledge`

#### 阶段二：检索（在线，每次提问跑一次，入口 FastAPI + LangGraph 图）

目标：根据用户提问，从索引库中捞出"刚好够用"的元数据，交给大模型生成并执行 SQL。

1. 提取关键词（jieba + 大模型扩展）；
2. **三路召回**：字段（Qdrant）、指标（Qdrant）、字段取值（ES）；
3. **合并召回**：把三路结果拼成"带字段列表的表信息列表"，并补齐主外键；
4. **二路过滤**：大模型筛掉与提问无关的表/字段、指标；
5. 补充额外上下文：当前日期、数据库类型与版本；
6. **生成 SQL → 校验 SQL →（失败则校正 SQL）→ 执行 SQL**，把执行结果流式推给前端。

**两阶段的关系**：索引决定了检索的**上限**——没有被索引进去的元数据，检索阶段永远召不回来，大模型也就写不出正确的 SQL。所以 `meta_config.yaml` 里字段的 `description` 和 `alias` 写得好不好，直接决定整个项目的效果。

### 4. 区别一下 json 与 yaml

**一句话结论**：两者都能表达"对象/数组/标量"的层级数据，**YAML 面向人写（配置文件），JSON 面向机器传（接口数据）**。

| 对比项 | YAML | JSON |
| --- | --- | --- |
| 语法风格 | 缩进表示层级，符号少 | 大括号、方括号、逗号、引号 |
| 可读性 | 好，接近自然书写 | 一般，符号噪音多 |
| 注释 | **支持**（`#`） | **不支持** |
| 单行书写 | 不适合（依赖缩进和换行） | **可以压成一行**，适合网络传输 |
| 解析性能 | 较慢，规范复杂 | 快，几乎所有语言原生支持 |
| 典型用途 | 配置文件（k8s、CI、本项目 conf） | 前后端数据传输、API 响应、日志 |
| 关系 | YAML 是 JSON 的超集（合法 JSON 基本是合法 YAML） | — |

**同一份数据的两种写法**

```yaml
# yaml：可以写注释，缩进表层级
qdrant:
  host: localhost
  port: 6333
  embedding_size: 1024   # 向量维度
```

```json
{"qdrant": {"host": "localhost", "port": 6333, "embedding_size": 1024}}
```

**YAML 的几个坑（易错点）**

- 只能用**空格**缩进，禁止用 Tab；
- 冒号后面必须有一个空格（`port: 6333`，不能写 `port:6333`）；
- `yes/no/on/off` 会被解析成布尔值，`1.0` 会被解析成浮点数，字符串有歧义时要加引号（如 `rotation: "10 MB"`）。

**项目落地**

- 配置用 YAML：`conf/app_config.yaml`（日志、MySQL、Qdrant、Embedding、ES、LLM）、`conf/meta_config.yaml`（表/字段/指标的人工描述）；
- 传输用 JSON：SSE 流式推送时 `json.dumps(chunk, ensure_ascii=False, default=str)`；元数据里的 `examples`、`alias`、`relevant_columns` 在 MySQL 中也用 `JSON` 类型列存储。

### 5. 说说 OmegaConf 库的 2 个作用

相对于直接用 `yaml.safe_load()` 得到一个 `dict`，OmegaConf 的两大好处是：

**作用一：把 YAML 数据转换成指定类型的结构化对象（读属性有提示）**

- 普通 `dict` 只能 `cfg["logging"]["file"]["level"]` 这样取值，**IDE 没有补全、写错 key 运行时才炸**；
- OmegaConf 可以把 `DictConfig` 和一个 `@dataclass` 结构合并，再 `to_object()` 生成真正的 dataclass 实例，之后就能 `app_config.logging.file.level` 这样点出来，**有补全、有跳转、有类型提示**。

**作用二：对属性名和属性值类型做约束校验（配置错误提前暴露）**

- 合并时会用 dataclass 做 schema 校验：YAML 里多写一个不存在的 key、或把 `port` 写成字符串，**在应用启动加载配置时就报错**，而不是等业务跑到一半才崩；
- 同时支持默认值、必填项（`MISSING`）、只读、变量插值 `${a.b}`、环境变量插值 `${oc.env:XXX}`、多份配置合并与命令行覆盖。

**项目落地**（`app/conf/app_config.py:85-89`）

```python
_yaml_path = Path(__file__).parents[2] / 'conf' / 'app_config.yaml'
_yaml_data = OmegaConf.load(_yaml_path)                                   # → DictConfig
app_config: AppConfig = OmegaConf.to_object(OmegaConf.merge(AppConfig, _yaml_data))  # → AppConfig 对象
```

- `AppConfig` 由一组 `@dataclass` 组成：`LoggingConfig / DBConfig / QdrantConfig / EmbeddingConfig / ESConfig / LLMConfig`（`app/conf/app_config.py:9-83`）；
- 同样的套路用在元数据配置上：`app/conf/meta_config.py:32-36`，生成 `meta_config: MetaConfig`；
- 模块级只加载一次，其他模块 `from app.conf.app_config import app_config` 直接用，相当于一个**全局单例配置**。

### 7. 后端项目的三层架构

**一句话结论**：按"谁负责什么"把后端切成**接口层 → 业务层 → 持久层**三层，上层只能调下层，下层不感知上层。

**（1）表现层 / 接口层（`app/api`）**

- 用 FastAPI 定义路由（接口），一个路由 = 一个请求路径 + 请求方式 + 路由函数；
- 负责**接收参数**（path / query / body）并做格式校验（Pydantic）；
- 调用业务层的方法，把结果封装成响应（本项目是 SSE 流式响应）返回给前端；
- **不写业务逻辑，不碰数据库**。

**（2）业务层（`app/services`）**

- 编排一次完整的业务动作：调用多个持久层方法、组织数据、处理业务规则；
- 事务边界通常也在这一层之上控制（本项目在入口脚本 / 依赖项里控制 session 的 commit/rollback）；
- 本项目两个典型 service：`MetaKnowledgeService`（构建知识库）、`QueryService`（问数查询，驱动 LangGraph 图）。

**（3）持久层（`app/repositories`）**

- 定义对各类存储的 CRUD 方法，屏蔽底层差异；
- 关系型数据库用 **ORM 框架**（SQLAlchemy），不用手写 SQL，基于对象操作，框架内部生成 SQL；
  > ORM = Object Relational Mapping 对象关系映射：类 ↔ 表，对象 ↔ 行，属性 ↔ 列。
- 本项目按存储分了三个子包：`mysql/`（`DWMysqlRepository`、`MetaMysqlRepository`）、`qdrant/`（字段/指标向量）、`es/`（字段取值）。

**（4）配套的支撑目录**

| 目录 | 职责 |
| --- | --- |
| `app/models` | 数据模型：`mysql/`（ORM 实体）、`qdrant/`（payload TypedDict）、`es/`（文档 TypedDict） |
| `app/clients` | 各中间件客户端管理器，负责 `init_client()` / `close()`，全局单例 |
| `app/conf` | 配置加载 |
| `app/core` | 公共基础设施：日志、上下文变量、生命周期 |
| `app/agent` | LangGraph 智能体（本项目特有的一层"编排层"） |

**调用方向**：`api → services → repositories → clients/models`，依赖**单向**，不能反向调用，也不能跨层直接从 api 调 repository（依赖注入组装除外）。

**好处**：职责单一、便于测试（可单独 mock 持久层）、便于替换（换数据库只动持久层）、多人协作时冲突少。

### 8. 说说 SQLAlchmy 库的特点

**一句话结论**：SQLAlchemy 是 Python 生态最主流的**关系型数据库 ORM 框架**，让你"用对象操作数据库"，框架内部自动生成并执行 SQL，同时自带连接池。

**核心特点**

1. **ORM 映射**：用一个 Python 类映射一张表，类属性映射列。定义方式（2.0 风格）：继承 `DeclarativeBase`，用 `Mapped[...]` + `mapped_column(...)` 声明。
   - 本项目：`app/models/mysql/base.py` 定义 `Base`，`TableInfoMySQL`、`ColumnInfoMySQL`、`MetricInfoMySQL`、`ColumnMetricMySQL` 四个实体。
2. **不用写 SQL**：`session.add()` 插入、`session.get()` 主键查询、`select(Model).where(...)` 条件查询、改属性即更新、`session.delete()` 删除。
3. **双层设计**：上层 ORM + 底层 Core。复杂 SQL 可以直接 `session.execute(text("select ..."))` 退回原生 SQL（本项目执行数仓查询 SQL 就是这么做的）。
4. **内置连接池**：`create_engine/create_async_engine` 创建的 Engine 维护一个连接池，避免每次操作都建立 TCP 连接和认证，显著提升效率。
5. **Session 工作单元（Unit of Work）**：session 跟踪对象状态（新增/修改/删除），`commit()` 时统一 flush 成 SQL 并提交事务，出错可 `rollback()`。
6. **方言（Dialect）机制**：同一套代码通过换连接串适配 MySQL / PostgreSQL / SQLite / Oracle。
7. **支持异步**：2.0 提供 `create_async_engine` / `AsyncSession` / `async_sessionmaker`，配合异步驱动（本项目用 `asyncmy`）在 asyncio 下不阻塞事件循环。
8. **`async_sessionmaker` 会话工厂**：把 engine 和一堆参数固定下来，之后 `async with factory() as session:` 一行就能拿到一个会话，用完自动关闭/归还连接。

**项目落地**（`app/clients/mysql_client_manager.py:17-33`）

```python
def _get_url(self):
    return f"mysql+asyncmy://{user}:{password}@{host}/{database}?charset=utf8mb4"

def init_client(self):
    self.client = create_async_engine(self._get_url(), pool_size=10, max_overflow=5)
    self.session_factory = async_sessionmaker(self.client, autobegin=True, autoflush=False)

async def close(self):
    await self.client.dispose()     # 关闭连接池中的所有连接
```

连接串三段式：`方言+驱动://用户:密码@主机/库名?参数`。项目里创建了两个管理器实例：`dw_mysql_client_manager`（数仓）、`meta_mysql_client_manager`（元数据库）。

### 9. 说说 SQLAlchmy 库中的下面几个配置的作用

前两个是 **Engine（连接池）** 的参数，后两个是 **Session（会话）** 的参数。

| 配置 | 归属 | 作用 | 默认值 | 本项目取值 |
| --- | --- | --- | --- | --- |
| `pool_size` | Engine | 连接池**常驻连接数**，池子初始/稳定保持的连接数量 | 5 | **10** |
| `max_overflow` | Engine | 常驻连接用完后允许额外创建的**临时连接数上限** | 10 | **5** |
| `autoflush` | Session | 查询前是否自动把内存中未提交的改动 flush 到数据库（事务内可见） | True | **False** |
| `autobegin` | Session | 是否在第一次操作时自动开启事务 | True | **True** |

**逐个展开**

- **`pool_size`**：池中长期保持的连接数。请求来了直接从池里借，用完还回去，避免频繁三次握手 + 认证。设置过小会排队，过大会浪费数据库连接资源。
- **`max_overflow`**：并发高峰时，常驻连接不够用，可以临时再开的连接数。所以**最大并发连接 = pool_size + max_overflow**（本项目 = 10 + 5 = 15）。超出后新的请求会阻塞等待，直到 `pool_timeout`（默认 30s）超时报错。临时连接归还后会被销毁，不会常驻。
- **`autoflush`**：开启时，执行 `select` 前 SQLAlchemy 会自动先把 session 中挂起的新增/修改 flush 出去，保证"刚 add 的数据在同一事务内能查到"。
  - 关掉（本项目 `False`）的好处：避免在批量构建过程中因为一次查询就触发意外的 SQL 写入、也避免半成品对象过早入库导致约束报错，写入时机完全由代码显式控制（统一 `commit()`）。
  - 注意区分：**flush = 把 SQL 发给数据库（还在事务里）；commit = 提交事务（真正落库）**。
- **`autobegin`**：为 True 时不需要手动 `session.begin()`，第一次执行语句就自动开启事务，之后统一 `commit()` 或 `rollback()`。这也是本项目"构建失败就整体回滚"能成立的前提。

**项目里的事务闭环**（`app/scripts/build_meta_knowledge.py`）：所有写操作先攒在 `meta_session` 中 → `await service.build()` 成功后 `await meta_session.commit()` → 抛异常则 `await meta_session.rollback()` 并重新抛出。

### 10. 说说 Qdrant 的作用

**一句话结论**：Qdrant 是一个开源的**向量数据库**，负责**高维向量的存储与相似度检索**，在本项目中承担**语义召回**（字段信息、指标信息）的职责。

**核心概念**

| 概念 | 含义 | 类比 |
| --- | --- | --- |
| collection | 一组同维度向量的集合 | 表 |
| point | 一条记录：`id` + `vector` + `payload` | 行 |
| vector | 向量（`list[float]`），本项目 1024 维 | — |
| payload | 挂在向量上的原始业务数据（JSON） | 其它列 |
| distance | 相似度度量：Cosine / Dot / Euclid | — |

**能力**

1. **相似度检索**：给一个查询向量，返回最相似的 Top-K point（`query_points(query=..., limit=..., score_threshold=...)`）；
2. **带过滤的检索**：`query_filter` 可按 payload 字段先过滤再算相似度（如只在某张表的字段里找）；
3. 支持 HNSW 近似最近邻索引、批量 upsert、持久化、REST/gRPC 接口和 Web UI（`http://localhost:6333/dashboard`）。

**⚠️ 关键注意点**：**Qdrant 本身不会生成向量**。文本 → 向量必须由外部的嵌入模型完成（本项目是 HuggingFace TEI 服务），Qdrant 只负责"存向量、比向量"。

**项目落地**

- 客户端：`app/clients/qdrant_client_manager.py`，`AsyncQdrantClient("http://localhost:6333")`；
- 两个集合：`data-agent_column_collection2`（字段）、`data-agent_metric_collection2`（指标）；
- 维度 `app_config.qdrant.embedding_size = 1024`，度量 `models.Distance.COSINE`；
- 建集合时"存在即先删再建"，方便反复构建测试（`column_qdrant_repository.py:13-25`）；
- **一个字段会生成多条 point**：字段名、字段描述、每个别名各一条向量，共用同一份 payload，这样"销售额/营业额/GMV"任一说法都能召回同一个字段。

### 11. 说说 Hugging Face 的作用

**一句话结论**：Hugging Face 提供了**模型生态 + 推理服务**，本项目用它把文本**批量转换成向量**（embedding），补上 Qdrant "不会生成向量"的那一环。

**两个层面理解**

1. **模型社区（Hub）**：全球最大的开源模型/数据集托管平台，可以下载各种嵌入模型、重排模型、大模型。本项目使用的嵌入模型是 **`BAAI/bge-large-zh-v1.5`**（中文语义嵌入，输出 1024 维向量）。
2. **推理服务（TEI / transformers）**：Hugging Face 的 Text Embeddings Inference 可以把嵌入模型部署成一个 HTTP 服务，对外提供 embedding 接口，支持批量、GPU 加速。本项目通过 Docker 把它跑在 `localhost:8081`。

**在 RAG 流程中的位置**

```
文本 --(HuggingFace 嵌入服务)--> 向量 --(Qdrant)--> 存储/检索 --> 相似结果
```

- 索引阶段：把字段名、字段描述、别名、指标名等转成向量写进 Qdrant；
- 检索阶段：把用户提问的关键词转成向量，去 Qdrant 做相似度匹配。
- **两边必须用同一个模型**，否则向量空间不一致，检索结果无意义。

**项目落地**（`app/clients/embedding_client_manager.py:14-15`）

```python
def init_client(self):
    self.client = HuggingFaceEndpointEmbeddings(model=f'http://{host}:{port}')
```

两个常用方法：

- `await client.aembed_query(text) -> list[float]`：单条文本转向量（检索时用）；
- `await client.aembed_documents(texts) -> list[list[float]]`：**批量**文本转向量（索引时用，本项目按 `batch_size=16` 分批调用，避免一次请求过大）。

### 12. 说说 ContextVar 的理解

**一句话结论**：`ContextVar` 是 Python 提供的**协程安全的上下文变量**——每个协程有自己独立的 context，互不干扰，可以在不层层传参的情况下，读写"当前这次执行链路"的数据。

**原理**

- 每个协程/任务执行时都关联一个 `Context` 对象，本质是一个字典：`{变量: 值}`；
- `ContextVar` 对象**本身不存数据**，它只是这个字典的**代理/key**，`set/get` 操作的是**当前协程的 context**；
- 协程切换时（`await`），context 也随之切换，所以并发的多个请求不会互相串数据。

```
协程1 的 context: {"req_id": "1111"}
协程2 的 context: {"req_id": "2222"}
两个协程调用同一个 ContextVar 的 get()，各自拿到自己的值
```

**API**

| 方法 | 说明 |
| --- | --- |
| `ContextVar("名字", default=...)` | 创建，`default` 是未设置时的返回值 |
| `token = var.set(value)` | 设置值，返回一个 `Token`（记录了上一个值） |
| `var.get()` | 取当前协程的值 |
| `var.reset(token)` | 用 token 把值恢复到 set 之前的状态 |

**类比**：`threading.local` 是"线程局部变量"，`ContextVar` 是它在**协程**场景的对应物（且同样兼容多线程）。

**为什么需要它**：日志想打印"这条日志属于哪个请求"，如果靠函数传参，就得把 `request_id` 从路由一路传到 service、repository，侵入性极大。用 ContextVar，中间件在请求入口 set 一次，任意深度的代码 get 一次即可。

**项目落地**（`app/core/context.py:6-15`）

```python
request_context_var = ContextVar('req_id', default='')

def set_request_id(req_id: str) -> Token:
    return request_context_var.set(req_id)

def get_request_id():
    return request_context_var.get()

def reset_request_id(token: Token):
    request_context_var.reset(token)
```

配合使用：FastAPI 中间件在调用路由函数前 `set_request_id(uuid4())`，日志模块通过 `logger.patch(inject_request_id)` 在每条日志里自动带上 `request_id`（`app/core/log.py:19-23`），这样并发请求的日志可以按 request_id 串起来排查。

### 13. 说说日志模块的功能特点

本项目用 **loguru** 封装日志（`app/core/log.py`），具备以下功能：

1. **自定义输出格式，按级别着色**
   格式包含：时间（精确到毫秒）、日志级别、**request_id**、模块名:函数名:行号、日志正文。定位问题时能直接看到是哪个文件哪一行打的日志。

2. **多目的地（sink）输出、分别控制级别**
   - 控制台 sink：`sys.stdout`，级别取 `app_config.logging.console.level`（INFO）；
   - 文件 sink：`log/app.log`，级别取 `app_config.logging.file.level`（INFO）。
   两个级别可以不同，例如控制台只看 INFO，文件里留 DEBUG 方便回溯。

3. **日志文件自动切割（rotation）**
   `rotation="10 MB"`：单个日志文件超过 10MB 就自动新建一个文件，避免出现几个 G 的巨型日志。也支持按时间切割（如 `"00:00"` 每天零点切）。

4. **日志文件自动清理（retention）**
   `retention="7 days"`：超过 7 天的历史日志自动删除，防止磁盘被写满。

5. **自动注入 request_id（本项目的关键设计）**
   ```python
   def inject_request_id(record):
       record["extra"]["request_id"] = get_request_id()

   logger = logger.patch(inject_request_id)
   ```
   `patch` 会在**每条日志输出前**执行该函数，从 ContextVar 中取出当前请求 id 塞进 `record["extra"]`，格式串里再用 `{extra[request_id]}` 打印出来。高并发下不同请求的日志可以精确区分。

6. **开箱即用的其他能力**
   - 级别齐全：`trace / debug / info / success / warning / error / critical`；
   - `logger.remove()` 先移除 loguru 的默认控制台 sink，避免重复输出；
   - 支持 `@logger.catch` 装饰器自动捕获并记录异常堆栈；
   - 相比标准库 `logging`，无需 Handler/Formatter/Filter 一堆样板代码。

**使用方式**：其他模块只要 `from app.core.log import logger`，直接 `logger.info(...)` 即可，配置集中在一处。

### 14. 说说你对 ES 的理解

**一句话结论**：Elasticsearch 是一个开源的**分布式全文搜索引擎**，底层基于 Lucene 的**倒排索引**，擅长在海量文本中做"字面/分词级"的快速检索。

**（1）核心原理：倒排索引**

普通数据库是"正排"：文档 → 有哪些词；倒排索引反过来："词 → 出现在哪些文档"。

- **建索引时**：文档内容先**分词**（中文用 IK 分词器）→ 去重合并 → 排序 → 形成"词项 → 文档 id 列表（含词频、位置）"的映射；
- **检索时**：把用户的查询串同样分词 → 拿每个词去倒排表里找 doc id → 合并、按相关性打分（TF-IDF / BM25）排序 → 根据 doc id 取回文档原文。

因此 ES 能做到"上亿文档里毫秒级找到包含某个词的文档"，这是 `like '%xx%'` 全表扫描做不到的。

**（2）分布式架构特点**

| 概念 | 说明 |
| --- | --- |
| 节点 node | 一个 ES 进程，多节点组成集群 |
| 分片 shard | 索引被水平切成多个分片分散到不同节点 → 支撑超大数据量（可到 PB 级）、并行检索 |
| 副本 replica | 分片的备份，节点宕机可顶上 → 高可用；同时能分担读请求 |
| 近实时 NRT | 写入后默认约 1 秒（refresh）才可被搜索到，所以测试时常需手动 `indices.refresh()` |

**（3）其他特点**

- 提供 **REST API**，用 JSON 描述查询（DSL），任何语言都能接入；
- Schema 由 mapping 定义，支持动态映射和静态映射；
- 除全文检索外还支持聚合分析（aggs），常与 Logstash/Kibana 组成 ELK 做日志分析；
- 新版本也支持向量检索（kNN），但本项目向量部分交给了 Qdrant。

**（4）与向量索引的分工（本项目的关键设计）**

| | 全文索引（ES） | 向量索引（Qdrant） |
| --- | --- | --- |
| 匹配方式 | **字面匹配**：分词后有相同词就能命中 | **语义匹配**：向量空间距离近就能命中 |
| 适合的数据 | **字段取值**（"华北"、"iPhone 15"、"黄金会员"） | **字段信息、指标信息**（名称/描述/别名） |
| 举例 | 提问里出现"华北" → 命中 `dim_region.region_name` 的取值 | 提问里说"营业额" → 命中字段"订单金额"/指标"销售总额" |

字段取值是专有名词，用语义相似度反而容易匹歪，所以走全文；字段/指标的说法千变万化（销售额=营业额=GMV），必须靠语义，所以走向量。**两者互补，缺一不可**。

### 15. ES 中的索引、文档和字段

**类比理解（最直观的记法）**

| ES 概念 | 关系型数据库类比 | 面向对象类比 | 说明 |
| --- | --- | --- | --- |
| 索引 index | 表 / 数据库 | 列表 | 一类文档的集合，有自己的 mapping 和分片设置 |
| 文档 document | 一行记录 | 一个对象 | ES 中数据的最小存储单位，本质是一个 JSON |
| 字段 field | 一列 | 对象的属性 | 文档中的一个键值对 |

> 注意：早期版本还有 type（类比表），7.x 之后已废弃，现在是"一个索引一种文档"。

**（1）索引 index**

- 命名只能小写，不能含空格；
- 通过 `mappings` 定义字段结构（相当于建表语句）：
  - `dynamic: true`（默认，动态映射）：写入未定义的字段会自动推断类型并加入 mapping；
  - `dynamic: false`（**静态映射**，本项目采用）：未定义的字段只存不索引，结构可控；
- 常用操作：`indices.exists` / `indices.create` / `indices.delete` / `indices.refresh`。

**（2）文档 document**

- 每个文档有唯一 `_id`（可指定，也可让 ES 自动生成）、`_index`、`_source`（原始 JSON）；
- 批量写入用 `bulk`，格式是"一行元数据 + 一行文档"交替：
  ```python
  operations = [{'index': {'_index': index_name}}, {...文档...}, ...]
  await client.bulk(operations=operations)
  ```

**（3）字段 field 的常见类型**

| 类型 | 是否分词 | 用途 |
| --- | --- | --- |
| `text` | **分词** | 全文检索的正文（本项目的 `value`） |
| `keyword` | 不分词，整体存储 | 精确匹配、过滤、聚合、排序（id、类型、表名） |
| `integer` / `float` / `date` / `boolean` | — | 数值、时间、布尔 |

还可以设置 `index: true/false`（是否建索引，false 则只存不可搜）、`analyzer`（分词器）。

**项目落地**（`app/repositories/es/value_es_repository.py:8-20`）

```python
index_name = 'data-agent-value_index2'
mappings = {
    "dynamic": False,                                                        # 静态映射
    "properties": {
        "id":          {"type": "keyword", "index": False},
        "value":       {"type": "text", "analyzer": "ik_max_word", "index": True},  # 唯一参与全文检索的字段
        "type":        {"type": "keyword", "index": False},
        "column_id":   {"type": "keyword", "index": False},
        "column_name": {"type": "keyword", "index": False},
        "table_id":    {"type": "keyword", "index": False},
        "table_name":  {"type": "keyword", "index": False},
    }
}
```

设计意图：只有 `value`（字段取值本身）需要被分词检索，用 IK 分词器 `ik_max_word`（最细粒度切分，召回率高）；其余字段只是**召回后要带出来的定位信息**（这个值属于哪个表的哪个字段），所以设为 `keyword` 且 `index: False`，既省索引空间又提升写入速度。

### 16. 什么是 REST API

**一句话结论**：REST（Representational State Transfer，表述性状态转移）是一种**接口设计风格**——**用 URL 定位资源，用 HTTP 请求方式表达对资源的操作**。

**（1）核心思想**

- URL 里只出现**名词（资源）**，不出现动词（操作）；
- 操作由 **HTTP 方法**表达：

| 方法 | 语义 | 示例 |
| --- | --- | --- |
| GET | 查询资源 | `GET /user/1` 查 id=1 的用户 |
| POST | 新增资源 | `POST /user` |
| PUT / PATCH | 更新（全量 / 局部） | `PUT /user/1` |
| DELETE | 删除资源 | `DELETE /user/1` |

- 用 **HTTP 状态码**表达结果：200 成功、201 已创建、400 参数错误、401 未认证、404 不存在、500 服务器异常；
- 数据格式通常用 **JSON**；
- **无状态**：每次请求自带全部信息，服务端不保存会话上下文，便于水平扩展。

**（2）REST 与非 REST 对比**

| | REST API | 非 REST API |
| --- | --- | --- |
| 路径 | `http://localhost:3000/user/1` | `http://localhost:3000/getUserById?id=1` |
| 一个路径 | 可对应**多种请求方式**，每种对应不同后台操作 | 只对应**一种**请求，一个路径一个操作 |
| 路径含义 | 只表示资源 | 路径里带操作名（get/add/update/delete） |
| 接口数量 | 少（一个资源一套） | 多（每个操作一个） |

**（3）FastAPI 中的写法**

```python
@app.get("/xxx")          # 同一路径，GET 请求走这里
async def test_get():
    return {"get message": "hello"}

@app.post("/xxx")         # 同一路径，POST 请求走这里
async def test_post():
    return {"post message": "hello"}
```

**（4）实际工程中的取舍**

严格 REST 并不总是最优。像本项目的"问数查询"接口 `POST /api/query`，它不是标准的资源增删改查，而是一个动作型接口，参数（用户提问）放在请求体里、用 POST 提交更合适，返回还是 SSE 流。所以**理解 REST 的思想 > 教条地套用 REST**。

### 17. ES 的查询

ES 使用 **DSL（Domain Specific Language）**，用一个 JSON 描述查询条件，通过 `client.search(index=..., query={...})` 发起。

**（1）单条件查询**

| 查询 | 是否分词 | 说明 | 示例 |
| --- | --- | --- | --- |
| `match` | **会**对查询词分词 | 模糊/全文匹配，任一分词命中即返回，按相关性打分 | `{"match": {"value": "华北地区"}}` |
| `term` | **不**分词 | 精确匹配，用于 keyword 字段、数值、布尔 | `{"term": {"table_id": "dim_region"}}` |
| `range` | — | 数值/日期区间，`gte/gt/lte/lt` | `{"range": {"page_count": {"gte": 300, "lte": 600}}}` |
| `match_phrase` | 会分词 | 短语匹配，要求词序相邻 | `{"match_phrase": {"value": "华北大区"}}` |
| `match_all` | — | 查全部 | `{"match_all": {}}` |

> **`match` 与 `term` 最容易混**：`match` 是"查询词分词后去比对索引里的词"，`term` 是"拿整个查询词原样去比对索引里的词"。对 `text` 类型字段用 `term` 常常查不到（因为索引里存的是分词后的结果）。

**（2）多条件组合查询：`bool`**

```json
{
  "query": {
    "bool": {
      "must":     [ {"match": {"value": "华北"}} ],
      "should":   [ {"match": {"value": "华东"}} ],
      "must_not": [ {"term":  {"type": "int"}} ],
      "filter":   [ {"term":  {"table_id": "dim_region"}} ]
    }
  }
}
```

| 子句 | 含义 | 是否参与打分 |
| --- | --- | --- |
| `must` | 必须全部满足（AND） | **是** |
| `should` | 满足其一即可（OR），满足越多分越高 | **是** |
| `must_not` | 必须都不满足（NOT） | 否 |
| `filter` | 必须满足，但**不计算相关性得分** | **否**（可被缓存，性能更好） |

**（3）常用辅助参数**

- 分页：`from` / `size`（默认返回 10 条）；
- 排序：`sort`；只返回部分字段：`_source: ["value","column_id"]`；
- 高亮：`highlight`；最小得分：`min_score`。

**（4）返回结果结构**

```python
result["hits"]["total"]["value"]      # 命中总数
result["hits"]["max_score"]           # 最高得分
result["hits"]["hits"]                # 命中文档列表
result["hits"]["hits"][0]["_source"]  # 第一个文档的原始 JSON
result["hits"]["hits"][0]["_score"]   # 相关性得分
```

**（5）项目落地：字段取值召回**

`recall_value` 节点对每个关键词发起一次检索，对 `value` 字段做 `match`（IK 分词后匹配），命中后从 `_source` 中取出 `column_id / column_name / table_id / table_name`，从而知道"用户提问里的'华北'是 `dim_region.region_name` 的一个取值"，最终把它作为**取值样例**补进字段信息，帮助大模型写出正确的 `where region_name = '华北'`。

### 19. 构建知识库的同步脚本（入口脚本）的执行流程

文件：`app/scripts/build_meta_knowledge.py`，入口 `asyncio.run(start_build())`。

**执行步骤**

1. **打日志**：`logger.info('开始构建元知识库')`。
2. **初始化各个客户端管理器**（5 个，顺序调用 `init_client()`）：
   - `dw_mysql_client_manager`（数仓 MySQL：建 engine + session 工厂）
   - `meta_mysql_client_manager`（元数据库 MySQL）
   - `es_client_manager`（AsyncElasticsearch）
   - `qdrant_client_manager`（AsyncQdrantClient）
   - `embedding_client_manager`（HuggingFace 向量服务）
3. **创建针对 dw 和 meta 两个库的 session 对象**（`async with` 双上下文，退出时自动关闭/归还连接）：
   ```python
   async with (
       dw_mysql_client_manager.session_factory()   as dw_session,
       meta_mysql_client_manager.session_factory() as meta_session
   ):
   ```
4. **创建各个持久层对象，并创建构建知识库的业务对象**：
   ```python
   service = MetaKnowledgeService(
       dw_mysql_repo      = DWMysqlRepository(dw_session),
       meta_mysql_repo    = MetaMysqlRepository(meta_session),
       value_es_repo      = ValueESRepository(es_client_manager.client),
       column_qdrant_repo = ColumnQdrantRepository(qdrant_client_manager.client),
       metric_qdrant_repo = MetricQdrantRepository(qdrant_client_manager.client),
       embedding_client   = embedding_client_manager.client
   )
   ```
5. **调用构建知识库的业务方法**：`await service.build()`。
6. **事务处理**：
   - 成功 → `await meta_session.commit()`，打印"构建元知识库完成"；
   - 失败 → `except` 中 `logger.error(...)` → `await meta_session.rollback()` → `raise` 重新抛出（不吞异常）。
7. **`finally` 中无论成败都关闭各个客户端**：`dw_mysql_client_manager.close()`、`meta_mysql_client_manager.close()`、`es_client_manager.close()`、`qdrant_client_manager.close()`（embedding 管理器只有 HTTP 调用，没有 `close()`）。

**几个设计要点（面试常被追问）**

- **为什么要两个 session？** dw 和 meta 是两个不同的库（不同 engine、不同连接池），必须各自建会话。dw 只读、不提交；只有 meta 写入，所以只对 `meta_session` 做 commit/rollback。
- **为什么事务放在入口脚本？** 整个构建是"一件事"，要么全部成功、要么整体回滚，事务边界必须在最外层。
- **为什么 finally 里关客户端？** 连接池、HTTP 连接都是外部资源，不释放会造成连接泄漏；`finally` 保证异常路径也能释放。
- **Qdrant/ES 不在事务里**：它们没有分布式事务，MySQL 回滚了但向量库/ES 已经写入 —— 项目通过"**每次构建先删集合/索引再重建**"来保证幂等，重跑一次即可覆盖。

### 20. 构建知识库的业务函数的执行流程

文件：`app/services/meta_knowledge_service.py` 的 `MetaKnowledgeService.build()`。

**总览：先处理"表 + 字段"，再处理"指标"，每部分都是"先入 MySQL，再建索引"。**

```
build()
 ├─ 0. clear_all()                       清空 meta 库旧数据
 ├─ 1. 处理表信息和字段信息
 │    ├─ 1.1 _save_table_infos_to_meta()      → table_info / column_info
 │    ├─ 1.2 _save_column_infos_to_qdrant()   → 字段向量索引
 │    └─ 1.3 _save_value_infos_to_es()        → 字段取值全文索引
 └─ 2. 处理指标信息
      ├─ 2.1 _save_metric_infos_to_meta()     → metric_info / column_metric
      └─ 2.2 _save_metric_infos_to_qdrant()   → 指标向量索引
```

**步骤 0：清空旧数据**

`meta_mysql_repo.clear_all()`：按 `column_metric → metric_info → column_info → table_info` 的顺序删除（**先删关联表再删主表**，避免外键约束/主键冲突），保证反复构建可重入。

**步骤 1.1：表信息和字段信息 → meta 库**

1. 遍历 `meta_config.tables`，每张表构造 `TableInfoMySQL(id=表名, name, role, description)`；
2. 调 `dw_mysql_repo.get_column_types(表名)`（底层 `SHOW COLUMNS FROM 表`）拿到 `{字段名: 字段类型}`；
3. 遍历该表配置的字段，调 `dw_mysql_repo.get_column_values(表名, 字段名)` 取**前 10 个去重取值**作为 `examples`；
4. 构造 `ColumnInfoMySQL`：`id = f'{表名}.{字段名}'`、`type` 来自数仓、`role/description/alias` 来自配置、`table_id = 表名`；
5. `save_table_infos(...)` / `save_column_infos(...)`（内部只是 `session.add_all`，尚未落库）；
6. **返回 `column_infos`**，供后续步骤复用（避免重复查询）。

> 亮点：**类型和取值样例从真实数仓自动采集，业务语义从 yaml 人工补充**，两者合并成一份完整字段元数据。取值样例非常关键——它让大模型知道"性别字段里存的是'男/女'还是'M/F'"。

**步骤 1.2：字段信息 → Qdrant 向量索引**

1. 每个字段构造一份 `ColumnInfoQdrant` payload（id/name/type/role/examples/description/alias/table_id）；
2. **一个字段生成多条向量文本**：字段名、字段描述、每一个别名各生成一条，各自 `uuid4()` 作为 point id，但**共用同一份 payload**；
   → 这样"销售额""营业额""金额"任一说法都能召回同一个字段，**大幅提高语义召回率**；
3. 拆成 `ids / payloads / texts` 三个平行列表；
4. 按 `batch_size=16` 分批调用 `embedding_client.aembed_documents(batch)` 生成向量（分批避免单次请求过大、超时）；
5. `column_qdrant_repo.insert_column_info_vectors(ids, payloads, vectors)` → 内部先"存在即删再建集合"，再按 `batch_size=10` 分批 `upsert`。

**步骤 1.3：字段取值 → ES 全文索引**

1. 先根据配置构造 `{'表名.字段名': sync}` 的字典，**只有 `sync: true` 的字段（主要是维度表的维度字段）才需要建取值索引**；
2. 对这些字段调 `dw_mysql_repo.get_column_values(table_id, name, 10000)` 取该字段的**全部去重取值**；
3. 每个取值构造一个 `ValueInfoES` 文档（value + 所属 column_id/column_name/table_id/table_name）；
4. `value_es_repo.insert_value_infos(...)` → 先删索引再重建 mapping，然后按 `batch_size=30` 分批 `bulk` 写入。

> 为什么只索引维度字段的取值？因为**只有维度值会出现在用户提问里**（"华北"、"iPhone"、"黄金会员"），并在 SQL 里用于 `where` 过滤；度量字段（金额、数量）的取值是数字，索引它没有意义，量还极大。

**步骤 2.1：指标信息 → meta 库**

遍历 `meta_config.metrics`：构造 `MetricInfoMySQL(id=指标名, name, description, relevant_columns, alias)`；同时为 `relevant_columns` 中的每个 `column_id` 构造一条 `ColumnMetricMySQL(column_id, metric_id)`，写入**指标-字段关联表**（多对多）。

> 这张关联表在检索阶段有大用：召回到"销售总额"这个指标后，可以顺藤摸瓜把它依赖的字段（`fact_order.order_amount` 等）一并带出来。

**步骤 2.2：指标信息 → Qdrant 向量索引**

与 1.2 完全同构：每个指标按"指标名 / 指标描述 / 每个别名"生成多条向量，共用一份 `MetricInfoQdrant` payload，`batch_size=16` 分批向量化后写入 `data-agent_metric_collection2` 集合。

**最后**：`build()` 返回后由入口脚本统一 `commit()`，MySQL 的所有写入这时才真正落库。

### 21. 说说 Graph 中的几个核心组件

LangGraph 用"**状态图**"来编排智能体：把复杂流程拆成一个个节点，用边把它们连起来，用状态在节点间传递数据。

**（1）状态 State**

- 一个包含多个可变数据的对象（本项目用 `TypedDict`），**在图的各个节点之间流转**，是节点之间唯一的通信媒介；
- 创建图时通过 `state_schema=` 指定类型，执行图时通过 `input=` 指定初始值；
- 节点**不需要返回完整状态**，只返回本节点产生的"**更新（部分字段）**"，LangGraph 自动把更新合并进全局状态；
- 若多个并行节点会写**同一个字段**，需要用 `Annotated[list, operator.add]` 之类的 **reducer** 声明合并方式，否则后写的会覆盖先写的。本项目三路召回分别写 `recall_columns` / `recall_metrics` / `recall_values`，两路过滤分别写 `table_infos` / `metric_infos`，**字段互不冲突，所以不需要 reducer**。

```python
class DataAgentState(TypedDict):
    query: str                                   # 用户提问
    keywords: list[str]                          # 关键词
    recall_columns: list[ColumnInfoQdrant]       # 召回的字段
    recall_metrics: list[MetricInfoQdrant]       # 召回的指标
    recall_values:  list[ValueInfoES]            # 召回的字段取值
    table_infos:  list[TableInfoState]           # 合并/过滤后的表（含字段）
    metric_infos: list[MetricInfoState]          # 合并/过滤后的指标
    date_info: DateInfoState                     # 当前日期信息
    db_info:   DBInfoState                       # 数据库信息
    sql: str                                     # 生成的 SQL
    error: str                                   # 校验错误信息（条件边的判据）
```

**（2）节点 Node**

- 就是一个**实现特定功能的函数**（同步/异步都行），入参是状态等，出参是"状态更新的字典"；
- 用 `state_graph.add_node("节点名", 函数)` 注册；
- 一个节点只干一件事（提关键词、召回字段、生成 SQL……），**职责单一**才便于复用和调试。

**（3）边 Edge**

- 边是 `A → B` 的连线：A 执行完后执行 B，并把最新的状态传给 B；
- **普通边** `add_edge(A, B)`：无条件跳转；
- **并行边**：`add_edge(A, B)` + `add_edge(A, C)` → B、C **并发执行**；反过来 `add_edge(B, D)` + `add_edge(C, D)` → D 会**等 B、C 都完成**才执行（天然的 fork-join）；
- **条件边** `add_conditional_edges(源节点, 判断函数, 分支映射)`：根据当前状态动态决定下一个节点，是实现"循环/重试/分支"的关键；
- `START` 是虚拟起点，`END` 是虚拟终点。

**（4）图 Graph**

- `StateGraph(state_schema=..., context_schema=...)` 创建；
- `add_node` / `add_edge` / `add_conditional_edges` 组装；
- `compile()` 编译成**可执行图** `CompiledGraph`（这一步会做结构校验，如是否有孤立节点、是否可达 END）；
- 执行方式：`invoke/ainvoke`（一次拿最终结果）、`stream/astream`（流式拿中间过程）；
- `graph.get_graph().draw_mermaid()` / `print_ascii()` 可以把结构图打印出来，非常适合调试和写文档。

**（5）额外的 Context（本项目重点）**

除了会变的 State，还有**不变的依赖** —— 各种 repository、embedding 客户端。它们通过 `context_schema=DataAgentContext` 声明，执行时用 `context=` 传入，节点里用 `runtime.context["xxx"]` 取。
**为什么要分开？** State 是"数据"，每次执行都在变；Context 是"依赖"，一次会话内固定不变。分开后节点函数不必 import 全局单例，可测试性更好（测试时传 mock 对象即可）。

### 22. 说说节点函数的几个重要参数

节点函数最多可以接收三个参数，**按需声明即可，不用的可以不写**：

```python
async def some_node(state: DataAgentState,
                    runtime: Runtime[DataAgentContext],
                    config: RunnableConfig) -> dict:
    ...
    return {"字段": 值}     # 只返回本节点的更新
```

**（1）`state`：状态对象（自定义类型）**

- 在各节点间传递的**可变数据**，类型在创建 `StateGraph` 时用 `state_schema` 指定，初始值在执行图时用 `input=` 指定；
- 节点里读：`state["query"]`；
- 节点里写：**不要直接改 state**，而是 `return {"keywords": [...]}` 返回更新，由框架合并。

**（2）`runtime`：`Runtime` 运行时对象**

包含三样东西：

| 属性 | 作用 |
| --- | --- |
| `runtime.context` | **静态上下文**，存放固定数据或依赖的外部模块（本项目 5 个 repository + embedding 客户端），类型由 `context_schema` 指定，值在执行图时用 `context=` 传入 |
| `runtime.stream_writer` | **向调用者输出自定义数据的函数**，调用后外部的 `astream(stream_mode="custom")` 就能立刻收到，本项目用来推送执行进度和最终查询结果 |
| `runtime.store` | 实现**跨会话长期记忆**的对象，默认存内存（本项目未使用） |

**（3）`config`：`RunnableConfig` 配置对象**

- 保存执行时传入的配置，最典型的是 `thread_id`（配合 checkpointer 做多轮会话记忆）、`recursion_limit`、`callbacks`、`tags` 等；
- 用法：`config["configurable"]["thread_id"]`。

**（4）补充：`stream_mode` 的三种取值（和 `stream_writer` 配套理解）**

| stream_mode | 外部收到的内容 |
| --- | --- |
| `updates` | 每个节点**返回的更新**（增量） |
| `values` | 每个节点执行后**合并完的完整 state** |
| `custom` | 节点里 `stream_writer(...)` 主动写出的**自定义数据** |

本项目用 `custom`：只把"当前进度"和"最终结果"推给前端，既不泄露内部状态，数据量也小。

### 23. Graph 编码的基本流程

**五步走：定义状态 → 定义上下文 → 写节点 → 组装图 → 编译执行。**

**第 1 步：定义状态类型**

```python
class DataAgentState(TypedDict):
    query: str
    keywords: list[str]
    sql: str
    error: str
```

**第 2 步：定义上下文类型（存固定依赖）**

```python
class DataAgentContext(TypedDict):
    dw_mysql_repo: DWMysqlRepository
    meta_mysql_repo: MetaMysqlRepository
    value_es_repo: ValueESRepository
    column_qdrant_repo: ColumnQdrantRepository
    metric_qdrant_repo: MetricQdrantRepository
    embedding_client: HuggingFaceEndpointEmbeddings
```

**第 3 步：定义节点函数（一个功能一个文件，放在 `nodes/` 下）**

```python
async def extract_keywords(state: DataAgentState, runtime: Runtime[DataAgentContext]) -> dict:
    runtime.stream_writer({"stage": "提取关键字"})   # 推进度
    query = state["query"]
    keywords = extract_tags(query, topK=5, allowPOS=allow_pos)
    keywords = list(set(keywords + [query]))
    return {"keywords": keywords}                    # 返回更新
```

**第 4 步：创建图、加节点、加边**

```python
state_graph = StateGraph(state_schema=DataAgentState, context_schema=DataAgentContext)

state_graph.add_node("extract_keywords", extract_keywords)      # 加节点
...
state_graph.add_edge(START, "extract_keywords")                 # 加边
state_graph.add_edge("extract_keywords", "recall_column")
...
state_graph.add_conditional_edges(                              # 加条件边
    "validate_sql",
    lambda state: 'execute_sql' if state.get('error') is None else 'correct_sql',
    {'execute_sql': 'execute_sql', 'correct_sql': 'correct_sql'}
)
state_graph.add_edge("execute_sql", END)
```

**第 5 步：编译 + 执行**

```python
compiled_graph = state_graph.compile()

# 流式执行
async for chunk in compiled_graph.astream(
        input=DataAgentState(query="华北地区销售总额"),
        context=DataAgentContext(dw_mysql_repo=..., ...),
        stream_mode="custom"):
    print(chunk)
```

**编码习惯建议**

- 节点函数一律 `async def`，内部 IO（数据库、ES、LLM）全部 `await`，避免阻塞事件循环；
- 每个节点 `try/except` + 日志，失败要么抛出、要么写入 `error` 字段交给条件边处理；
- 先用 `print(compiled_graph.get_graph().draw_mermaid())` 把图打印出来，确认结构无误再接真实逻辑；
- 可以先把所有节点写成 `return {}` 的空壳，把图跑通，再逐个填实现（本项目就是这个开发节奏）。

### 24. 说一下项目中 Graph 编排的整个节点流程

**（1）结构图（12 个节点）**

```
                         START
                           │
                   ┌───────▼────────┐

                   └───┬───┬───┬────┘
          ┌────────────┘   │   └────────────┐
          ▼                ▼                ▼
   recall_column     recall_metric     recall_value        ← 三路并行召回
   (Qdrant 字段)      (Qdrant 指标)      (ES 字段取值)
          └────────────┐   │   ┌────────────┘
                       ▼   ▼   ▼
              ┌────────────────────────┐
              │  merge_retrieved_info  │                   合并三路召回
              └───────┬────────┬───────┘
                      ▼        ▼
              filter_table  filter_metric                  ← 两路并行过滤
                      └───┬────┘
                          ▼

                          ▼
                    generate_sql                           大模型生成 SQL
                          ▼
                    validate_sql                           EXPLAIN 校验
                     ╱          ╲
        error is None            error 非空
             ▼                        ▼
        execute_sql  ◄──────────  correct_sql              大模型校正 SQL
             ▼
            END
```

**（2）逐段说明**

| 阶段 | 节点 | 做什么 |
| --- | --- | --- |
| ① 理解提问 | `extract_keywords` | jieba 抽关键词 + 把原始提问一并保留 |
| ② 三路并行召回 | `recall_column` | 关键词 → 向量 → Qdrant 字段集合，召回相关**字段** |
| | `recall_metric` | 关键词 → 向量 → Qdrant 指标集合，召回相关**指标** |
| | `recall_value` | 关键词 → ES `match`，召回相关**字段取值** |
| ③ 汇总 | `merge_retrieved_info` | 三路结果去重合并成"带字段列表的表信息列表" + 指标列表 |
| ④ 两路并行过滤 | `filter_table` | 大模型裁掉与提问无关的表和字段 |
| | `filter_metric` | 大模型裁掉与提问无关的指标 |
| ⑤ 补充上下文 | `add_extra_context` | 当前日期/星期/季度、数据库方言与版本 |
| ⑥ 产出 SQL | `generate_sql` | 大模型根据 query + 表 + 指标 + 日期 + 库信息生成 SQL |
| ⑦ 质量闭环 | `validate_sql` | `EXPLAIN` 校验语法与对象存在性 |
| | `correct_sql` | 校验失败时，带着 SQL + 错误信息让大模型重写 |
| ⑧ 出结果 | `execute_sql` | 真正执行 SQL 查数仓，`stream_writer` 把结果推给前端 |

**（3）编排设计的三个亮点**

1. **并行**：三路召回互不依赖，用分叉边并发执行，总耗时 ≈ 最慢的一路，而不是三路之和；过滤同理。
2. **由粗到细的漏斗**：召回追求**高召回率**（宁多勿漏，一个字段建多条向量），过滤追求**高准确率**（把噪声裁掉，缩短提示词、提升 SQL 准确率、省 token）。
3. **可自愈的闭环**：`validate_sql` 的条件边形成"生成 → 校验 → 校正 → 执行"的纠错链路，把大模型的不确定性用数据库的确定性兜住。

> 补充：当前仓库中图的骨架（12 节点 + 并行边 + 条件边 + `compile()`）已经完整搭好（`app/agent/graph.py:32-74`），`extract_keywords` 已实现，其余节点尚为占位实现，完整实现见课件第 6.3 章。

### 25. 说下提取关键字节点的功能

文件：`app/agent/nodes/extract_keywords.py`，图的第一个节点。

**功能**

1. **用 jieba 做字面关键词提取**
   ```python
   keywords: list[str] = extract_tags(query, topK=5, allowPOS=allow_pos)
   ```
   - `jieba.analyse.extract_tags` 基于 **TF-IDF** 算法给词打分，取分值最高的 `topK=5` 个；
   - `allowPOS` 限定词性（名词 n、地名 ns、机构名 nt、动词 v、英文 eng 等 12 类），**过滤掉"的、了、吗、请问"这类无意义的虚词**；
   - 结果是一组能代表提问主题的词，如"华北地区销售总额" → `['华北', '地区', '销售', '总额']`。

2. **把用户原始提问也合并进关键词列表（兜底）**
   ```python
   keywords = list(set(keywords + [query]))
   ```
   - **为什么？** jieba 只做字面切分，**会丢语义**。比如"去年卖得最好的手机"，切完是"去年/卖/手机"，"卖得最好"这层"按销量排序取 Top1"的语义就没了；
   - 把整句提问作为一个"关键词"保留下来，后续做向量召回时，**整句的语义向量**往往比零散的词更能命中正确的字段/指标；
   - `set(...)` 顺带做去重。

3. **推送进度**：`runtime.stream_writer({"stage": "提取关键字"})`，让前端能显示"正在提取关键字…"。

4. **返回更新**：`return {"keywords": keywords}`。

**这个节点的定位**

它是整条召回链路的**输入源**：三路召回都以 `state["keywords"]` 为起点。所以它的原则是"**宁可多，不可漏**"——关键词漏了，后面再准的召回也捞不回来。这也是为什么后面三路召回还会各自再用大模型对关键词做一次**语义扩展**（见第 26 题），jieba 只是第一道粗筛，成本低、速度快、不花 token。

### 26. 说下三路召回节点的实现

三路召回由 `extract_keywords` 分叉出来**并行执行**，分别负责"字段、指标、字段取值"三类元数据。

**（1）共同套路（三路一致）**

1. 取出 `state["query"]` 和 `state["keywords"]`；
2. 用**大模型 + 各自的 prompt** 对提问做**语义化关键词扩展**，把扩展结果与 jieba 的关键词 `set()` **去重合并**；
   - 链式写法：`PromptTemplate | llm | JsonOutputParser`；
3. 用扩展后的每个关键词去对应的索引库检索；
4. 对检索结果**按 id 去重合并**，返回列表。

> 为什么要大模型扩展？用户说"营业额"，索引里存的是"订单金额"；用户说"华北"，字段名叫 `region_name`。**字面和语义之间有鸿沟**，让大模型先把提问翻译成"数据库里可能怎么叫"，召回率会显著提升。

**（2）三路的差异**

| | recall_column（召回字段） | recall_metric（召回指标） | recall_value（召回字段取值） |
| --- | --- | --- | --- |
| prompt | `extend_keywords_for_column_recall.prompt` | `extend_keywords_for_metric_recall.prompt` | `extend_keywords_for_value_recall.prompt` |
| 扩展目标 | 回答该问题**需要哪些字段名** | 涉及哪些**指标概念** | 提问里哪些词可能是**字段的取值** |
| 是否向量化 | **是**，`aembed_documents(keywords)` | **是** | **否**，直接用文本 |
| 检索库 | Qdrant `data-agent_column_collection2` | Qdrant `data-agent_metric_collection2` | ES `data-agent-value_index2` |
| 检索方式 | 向量相似度 `query_points`（带 `score_threshold`，如 0.6） | 向量相似度 `query_points` | `match` 全文检索（IK 分词） |
| 去重键 | `column_id` | `metric_id` | value 的 id |
| 写入状态 | `recall_columns: list[ColumnInfoQdrant]` | `recall_metrics: list[MetricInfoQdrant]` | `recall_values: list[ValueInfoES]` |
| 进度输出 | `{"stage": "召回字段"}` | `{"stage": "召回指标"}` | `{"stage": "召回字段值"}` |

**（3）为什么要分三路（而不是一路）**

- **索引类型不同**：字段/指标靠**语义**（同义词多），字段取值靠**字面**（专有名词，语义匹配反而会匹歪）；
- **信息作用不同**：
  - 字段 → 告诉大模型"有哪些列可用"；
  - 指标 → 告诉大模型"业务口径怎么算"（如"销售总额 = sum(order_amount)"）；
  - 字段取值 → 告诉大模型"'华北'这个词是 `dim_region.region_name` 的一个值"，从而写对 `where` 条件；
- **三路互补**：只召回字段，可能不知道口径；只召回指标，可能缺关联字段；没有取值，`where` 条件就会写错列。

**（4）为什么设置 `score_threshold`**

相似度低于阈值的结果基本是噪声，放进提示词只会干扰大模型、浪费 token。阈值是**召回率与准确率的权衡旋钮**：调低召回更多但更吵，调高更干净但可能漏。

### 27. 说下合并召回节点的实现

节点 `merge_retrieved_info` 是三路召回的**汇合点**（三条边都指向它，LangGraph 会等三路都完成才执行）。它的任务是把三份异构的召回结果，整理成大模型能直接读懂的两份数据：`table_infos` 和 `metric_infos`。

**第 1 步：收集一份最完整的字段列表，去重合并成 `dict[column_id, ColumnInfoQdrant]`**

用字典去重，key 是字段 id（形如 `fact_order.order_amount`）：

- **1.1 收集召回的字段信息列表**
  遍历 `recall_columns`，id 不在字典里就放进去。

- **1.2 收集召回的指标所关联的字段信息列表**
  遍历 `recall_metrics` 的 `relevant_columns`，对字典里缺失的 `column_id`，用 `meta_mysql_repo.get_column_info_by_id(column_id)` 去 meta 库补查，转成 `ColumnInfoQdrant` 后放入。
  > **意义**：召回到"销售总额"这个指标，就必须把它依赖的 `order_amount` 等字段一并带上，否则大模型知道口径却不知道用哪一列。

- **1.3 收集召回的字段取值所对应的字段信息列表，并把取值补进样例**
  遍历 `recall_values`：
  - 若该 `column_id` 不在字典里，同样去 meta 库补查后放入；
  - **把命中的 value 追加到该字段的 `examples` 列表**中。
  > **意义**：这是最关键的一步。用户说"华北"，ES 告诉我们它是 `dim_region.region_name` 的取值，把"华北"塞进该字段的样例里，大模型就能写出 `where region_name = '华北'` 而不是瞎猜。

- **1.4 收集相关表的主键和外键字段信息列表**
  对涉及到的每个 `table_id`，调 `meta_mysql_repo.get_key_column_infos_by_table_id(table_id)` 把该表的主键/外键字段补进来。
  > **意义**：多表查询必须 JOIN，JOIN 就要用主外键。这些字段在语义上和用户提问毫无关系（`customer_id` 不会被"华北销售额"召回），**只能靠规则强行补齐**，否则大模型无法正确关联事实表和维度表。

**第 2 步：根据收集到的字段列表，生成"带字段信息列表的表信息列表"**

- **2.1 按 `table_id` 分组**：`dict[table_id, list[ColumnInfoQdrant]]`；
- **2.2 生成 `table_infos: list[TableInfoState]`**：
  - 对每个 `table_id`，用 `meta_mysql_repo.get_table_info_by_id(table_id)` 查出表的元数据（name / role / description）；
  - 把该组字段逐个转换成 `ColumnInfoState`（name / type / role / examples / description / alias）；
  - 组装成 `TableInfoState(name, role, description, columns=[...])`。

**第 3 步：整理指标**

把 `recall_metrics` 逐个转成 `MetricInfoState`（name / description / relevant_columns / alias），得到 `metric_infos`。

**返回**：`{"table_infos": table_infos, "metric_infos": metric_infos}`。

**为什么要做这层转换（从"平铺的字段"到"按表组织"）**

大模型写 SQL 的思维是"**先选表，再选列，再 JOIN**"。平铺的字段列表让它难以判断哪些列属于同一张表、能不能 JOIN；组织成"表 → 字段"的树形结构后，提示词里呈现的就是一份**小型的、只跟本次提问相关的数据字典**，大模型的准确率会明显提高。

### 28. 说说合并召回后的节点实现

合并之后还有 6 类节点，可以分成"**二路过滤 → 补充上下文 → SQL 三部曲 + 执行**"。

**（1）二路过滤（并行）**

召回阶段是"宁多勿漏"，所以结果里有噪声；过滤阶段用大模型做**精筛**。

- **`filter_table`（过滤表和字段）**
  - 输入：`query` + `table_infos`（`yaml.dump` 后注入提示词，比 JSON 更省 token、更易读）；
  - 提示词：`filter_table_info.prompt`，要求大模型输出 `{"表名": ["字段名1", "字段名2"]}` 的 JSON；
  - 链路：`PromptTemplate | llm | JsonOutputParser`；
  - 处理：按大模型返回的结果，把不需要的**表**整个删掉、把表里不需要的**字段**删掉；
  - 返回：`{"table_infos": 过滤后的列表}`。

- **`filter_metric`（过滤指标）**
  - 输入：`query` + `metric_infos`；提示词 `filter_metric_info.prompt`，输出需要的指标名数组（可以是空数组）；
  - 处理：删掉未被选中的指标；返回 `{"metric_infos": 过滤后的列表}`。

> **为什么必须过滤？** ① 提示词长度和 token 成本；② 无关表/字段是强干扰项，容易让大模型 JOIN 错表、选错列；③ 上下文越长，大模型对关键信息的注意力越容易被稀释。

**（2）`add_extra_context`（添加额外信息）**

不调用大模型，纯粹补两类"环境信息"：

- **当前日期信息** `date_info`：日期、星期、季度（`datetime.today()` 计算）。
  > 用户会说"去年"、"上个月"、"本季度"，这些是**相对时间**，大模型不知道今天是几号就无法换算成 `where year = 2025`。
- **当前数据库信息** `db_info`：方言（MySQL）和版本（通过 `dw_mysql_repo` 查 `select version()`）。
  > 不同数据库、不同版本的 SQL 语法不同（日期函数、`limit` 写法、窗口函数支持度），告诉大模型目标环境才能生成**可执行**的 SQL。

返回：`{"date_info": ..., "db_info": ...}`。

**（3）`generate_sql`（生成 SQL）**

- 输入 5 项：`query`、`table_infos`、`metric_infos`、`date_info`、`db_info`，各自 `yaml.dump(..., allow_unicode=True, sort_keys=False)` 后填入 `generate_sql.prompt`；
- 链路：`PromptTemplate | llm | StrOutputParser`；
- 返回：`{"sql": sql}`。

**（4）`validate_sql`（校验 SQL）**

- 调 `dw_mysql_repo.validate_sql(sql)`，核心是：
  ```python
  await self.session.execute(text(f"explain {sql}"))
  ```
- **用 `EXPLAIN` 的妙处**：让数据库的解析器/优化器去解析这条 SQL，能发现**语法错误、表不存在、字段名写错、JOIN 写法错误**等真实问题，**但不会真正执行查询**，代价极低、也不会因为大数据量把库拖垮；
- 校验通过 → 返回 `{"error": None}` → 条件边跳 `execute_sql`；
- 校验失败 → 捕获异常，返回 `{"error": "SQL语法错误：..."}` → 条件边跳 `correct_sql`。

**（5）`correct_sql`（校正 SQL）**

- 在生成 SQL 的全部输入基础上，**额外加上出错的 `sql` 和 `error` 信息**，用 `correct_sql.prompt` 让大模型做"最小必要修正"，保持业务语义不变；
- 返回：`{"sql": 新的 sql}`；之后固定流向 `execute_sql`。

> 注意本项目的校正是**一次性**的（`correct_sql → execute_sql`），没有再回到 `validate_sql` 形成循环。要做成"最多重试 N 次"，只需把 `correct_sql` 连回 `validate_sql`，并在状态里加一个重试计数器、在条件函数里判断次数上限（否则可能死循环）。

**（6）`execute_sql`（执行 SQL）**

- 取出最终 `sql`，调 `dw_mysql_repo.execute_sql(sql)` 真正到数仓查询；
- 用 `runtime.stream_writer({"result": result})` 把**查询结果**推给外部调用者，前端接到后渲染成表格/图表；
- 之后流向 `END`，整张图结束。

**（7）串起来看这一段的设计哲学**

> 召回（宁多勿漏）→ 过滤（去噪提纯）→ 补环境（消除歧义）→ 生成（大模型只负责翻译）→ 校验（数据库把关）→ 校正（自愈）→ 执行（数据库出答案）。
> **大模型只在"语言理解"的环节出现，所有"事实与计算"都交给数据库**，这正是 NL2SQL 类项目可靠性的来源。

### 29. 说说 FastAPI 中的接口的参数

HTTP 请求携带文本参数有三种方式，FastAPI **根据路由函数形参的"写法"自动判断该从哪里取值**，并自动做类型转换和校验。

| 参数类型 | 在请求中的位置 | 路由函数如何声明 |
| --- | --- | --- |
| **path 参数** | 路径中可变的那一段 | 形参名与路由路径中的 `{占位名}` **同名** |
| **body 参数** | 请求体（一般 JSON） | 形参类型是 **`BaseModel` 的子类** |
| **query 参数** | 路径 `?` 后面的键值对 | **其余的普通形参** |

**完整示例**

```python
from pydantic import BaseModel

class MyBody(BaseModel):
    age: int
    sex: str

@app.post("/api/user/{id}")
def test_three_params(body: MyBody, id: int, name: str):
    #   body ← 请求体 JSON      id ← 路径占位      name ← ?name=xxx
    return {"id": id, "name": name, "age": body.age, "sex": body.sex}
```

请求：`POST http://localhost:8001/api/user/12?name=tom`，请求体 `{"age": 12, "sex": "男"}`。

**要点补充**

1. **自动类型转换与校验**：形参标了 `id: int`，传 `/api/user/abc` 会直接返回 422 错误，不用自己写校验代码；
2. **必填与可选**：`name: str` 是必填；`name: str = "默认值"` 或 `name: str | None = None` 是可选；
3. **Pydantic 模型的价值**：body 参数用 `BaseModel` 定义结构后，字段类型、必填性都会被校验，还会自动出现在 `/docs` 的交互文档里；
4. **自动生成文档**：启动后访问 `http://127.0.0.1:8000/docs`（Swagger UI）即可看到所有接口和参数并直接测试。

**项目落地**：问数查询接口只需要一个 `query` 字符串，用 body 传递：

```python
# app/api/schemas/query_schema.py
class QuerySchema(BaseModel):
    query: str

# app/api/routers/query_router.py
@query_router.post("/api/query")
async def search(query_schema: QuerySchema,
                 service: QueryService = Depends(get_query_service)):
    return StreamingResponse(service.search(query_schema.query),
                             media_type="text/event-stream")
```

> 为什么用 POST + body 而不是 GET + query？用户提问可能很长、含中文和特殊字符，放 URL 里既有长度限制又要转义，放请求体更合适。

### 30. 说说 FastAPI 的流式输出

**需求**：问数要经过"提关键词 → 三路召回 → 过滤 → 生成 SQL → 校验 → 执行"很多步，全部跑完可能十几秒。如果等全部结束再一次性返回，用户会盯着空白页面干等。所以要**边执行边把进度和结果推给浏览器**。

**技术选型：SSE（Server-Sent Events）**

| | SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | **服务端 → 客户端单向** | 双向 |
| 协议 | 普通 HTTP | 独立的 ws 协议，需要握手升级 |
| 实现复杂度 | 低，浏览器原生 `EventSource` | 较高 |
| 适用场景 | 推送进度、流式输出（**本项目**） | 聊天室、协同编辑 |

本项目只需要服务端单向推送，**SSE 足够且更简单**。

**实现三要素**

1. **路由函数返回 `StreamingResponse`，并指定 `media_type="text/event-stream"`**（这个类型不能少，否则浏览器不会按 SSE 处理）：
   ```python
   @app.get("/api/stream")
   def test_stream():
       return StreamingResponse(fake_streamer(), media_type="text/event-stream")
   ```
2. **流式输出函数是一个"含 `yield` 的 async 函数"，即异步生成器**：每 `yield` 一次，客户端就能立刻收到一段数据；
3. **数据格式必须是 `data: 内容\n\n`**（`data:` 前缀 + **两个换行**表示一条消息结束），这是 SSE 协议规定的。

**项目落地**（`app/services/query_service.py`）

```python
async def search(self, query: str):
    try:
        state = DataAgentState(query=query)                 # 图的初始状态
        context = DataAgentContext(dw_mysql_repo=..., ...)  # 图的固定依赖
        async for chunk in compiled_graph.astream(
                input=state, context=context, stream_mode="custom"):
            # chunk 形如 {"stage": "召回字段"} 或 {"result": [{...}, {...}]}
            yield f"data: {json.dumps(chunk, ensure_ascii=False, default=str)} \n\n"
    except Exception as e:
        yield f"data: {json.dumps({'error': str(e)}, ensure_ascii=False, default=str)} \n\n"
```

**串起来的数据流**

```
节点内 runtime.stream_writer({"stage": "生成SQL"})
   → compiled_graph.astream(stream_mode="custom") 产出 chunk
   → QueryService.search 把 chunk 包成 "data: {...}\n\n" 并 yield
   → StreamingResponse 逐段写回
   → 浏览器 EventSource.onmessage 实时渲染进度条 / 结果表格
```

**两个细节**

- `json.dumps(..., ensure_ascii=False)`：保留中文原样，否则会变成 `\uXXXX` 转义；
- `default=str`：`chunk` 里可能有 `datetime`、`Decimal` 等 JSON 不支持的类型（数据库查询结果很常见），用 `str()` 兜底，避免序列化直接抛异常；
- **异常也要 yield 出去**：流已经开始响应了，不能再改 HTTP 状态码，所以错误必须作为一条 `data:` 消息推给前端。

### 31. 说说 FastAPI 中的生命周期与中间件

两者都是"在业务代码之外插入统一逻辑"的机制，区别在于**执行频率**：生命周期是**整个应用**级别（各一次），中间件是**每个请求**级别。

**（1）生命周期 lifespan**

- **作用**：在应用**启动时**和**停止前**各执行一次特定逻辑；
- **写法**：用 `@asynccontextmanager` 装饰的异步函数，`yield` 前是启动逻辑、`yield` 后是收尾逻辑，再绑定到 `FastAPI(lifespan=lifespan)`；

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # ---- 应用启动时执行一次：初始化客户端管理器 ----
    embedding_client_manager.init_client()
    qdrant_client_manager.init_client()
    es_client_manager.init_client()
    meta_mysql_client_manager.init_client()
    dw_mysql_client_manager.init_client()

    yield        # 应用运行中，处理请求

    # ---- 应用停止前执行一次：释放资源 ----
    await qdrant_client_manager.close()
    await es_client_manager.close()
    await meta_mysql_client_manager.close()
    await dw_mysql_client_manager.close()

app = FastAPI(lifespan=lifespan)
```

- **为什么要这样做**：数据库连接池、ES/Qdrant 客户端都是**重量级资源**，必须在应用启动时创建一次并全程复用；如果每个请求都新建，性能极差且会耗尽连接。停止前关闭则避免连接泄漏。

**（2）中间件 middleware**

- **作用**：在**每一个**请求被路由函数处理**之前**和**之后**插入统一逻辑；
- **写法**：`@app.middleware("http")` 装饰的异步函数，必须接收 `request` 和 `call_next`，并**返回 response**；
- `await call_next(request)` 这一行就是"调用后续中间件 / 目标路由函数"的分界线：

```python
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    # —— 调用路由函数之前：为本次请求生成唯一 id 并存入 ContextVar ——
    set_request_id(str(uuid.uuid4()))

    response = await call_next(request)     # 执行路由函数，拿到响应

    # —— 调用路由函数之后：可做耗时统计、加响应头等 ——
    return response
```

- **本项目的用途**：给每个请求生成唯一 `request_id` 存进 ContextVar，这样这次请求链路上打的所有日志都会自动带上同一个 id（见第 12、13 题），并发排查问题时可以按 id 把一次请求的日志全部串起来。
- **其他常见用途**：统计接口耗时并写入响应头、统一异常兜底、CORS 跨域、请求日志、限流。

**（3）对比总结**

| | lifespan 生命周期 | middleware 中间件 |
| --- | --- | --- |
| 触发时机 | 应用启动 / 停止 | 每个请求前 / 后 |
| 执行次数 | 各一次 | 每请求一次 |
| 分界写法 | `yield` | `await call_next(request)` |
| 典型用途 | 初始化/关闭客户端、加载模型 | 请求 id、耗时统计、鉴权、跨域 |

### 32. 说说 FastAPI 中的依赖注入

**描述**：路由函数需要用到的对象（service、数据库 session、当前登录用户……），**不在路由函数里自己 new**，而是通过形参声明 `= Depends(依赖函数)`，由 FastAPI 在处理请求时**自动调用依赖函数创建好，再注入进来**。

**作用**

1. **解耦**：路由函数不再"写死"依赖对象的创建过程，换实现只改依赖函数；
2. **复用**：鉴权、参数校验、资源获取等通用逻辑抽成依赖，多个接口共享；
3. **可组合**：**依赖函数本身还可以有依赖**，形成一棵依赖树，FastAPI 自动按顺序解析；
4. **可测试**：测试时用 `app.dependency_overrides` 一行替换成 mock 对象；
5. **自动管理资源**：`yield` 型依赖可以在请求结束后自动做清理。

**（1）普通依赖**

```python
def get_value_es_repo():
    return ValueESRepository(es_client_manager.client)

@app.get("/di/{id}")
def test_di(id: int, value_es_repo: ValueESRepository = Depends(get_value_es_repo)):
    ...
```

**（2）`yield` 型依赖（带清理动作，最常用于数据库 session）**

```python
async def get_dw_session():
    async with dw_mysql_client_manager.session_factory() as session:
        yield session      # 把 session 交给路由函数使用；请求结束后回到这里，退出 async with 自动关闭
```

执行时序：

```
请求进来 → 进入 async with（创建 session）→ yield 把 session 交出去
                                                  ↓
                                      路由函数/业务代码使用 session
                                                  ↓
请求结束 → 回到 yield 之后 → 退出 async with（自动关闭/归还连接）
```

> **易错点**：这里必须用 `yield` 而不是 `return`。用 `return` 会在返回的瞬间就退出 `async with` 把 session 关掉，路由函数拿到的是一个已关闭的会话。

**（3）依赖的嵌套组合（本项目的完整链条）**

```python
def get_dw_mysql_repo(session: AsyncSession = Depends(get_dw_session)):
    return DWMysqlRepository(session)

def get_meta_mysql_repo(session: AsyncSession = Depends(get_meta_session)):
    return MetaMysqlRepository(session)

def get_value_es_repo():       return ValueESRepository(es_client_manager.client)
def get_column_qdrant_repo():  return ColumnQdrantRepository(qdrant_client_manager.client)
def get_metric_qdrant_repo():  return MetricQdrantRepository(qdrant_client_manager.client)
def get_embedding_client():    return embedding_client_manager.client

def get_query_service(
    dw_mysql_repo:      DWMysqlRepository      = Depends(get_dw_mysql_repo),
    meta_mysql_repo:    MetaMysqlRepository    = Depends(get_meta_mysql_repo),
    value_es_repo:      ValueESRepository      = Depends(get_value_es_repo),
    column_qdrant_repo: ColumnQdrantRepository = Depends(get_column_qdrant_repo),
    metric_qdrant_repo: MetricQdrantRepository = Depends(get_metric_qdrant_repo),
    embedding_client:   HuggingFaceEndpointEmbeddings = Depends(get_embedding_client),
):
    return QueryService(...)

# 路由里只需要声明最终要用的那一个
@query_router.post("/api/query")
async def search(query_schema: QuerySchema, service: QueryService = Depends(get_query_service)):
    ...
```

依赖树：`路由 → QueryService → 5 个 repository → session/client`。**路由函数只写一个 `Depends(get_query_service)`，整棵树由 FastAPI 自动装配**，这与构建知识库脚本里手工 new 一堆对象形成鲜明对比 —— 后者是脚本（只跑一次，手工组装即可），前者是长期服务（每个请求都要组装，交给框架）。

### 33. 理解 FastAPI 中的路由和路由器

**（1）路由 Route**

- **一个路由 = 一个接口**，由三部分构成：**请求路径 + 请求方式 + 路由函数（处理请求的函数）**；
- 用装饰器注册：`@app.get("/xxx")`、`@app.post("/xxx")`、`@app.put(...)`、`@app.delete(...)`；
- 当客户端请求这个路径且方式匹配时，FastAPI 自动调用对应的路由函数，并把返回值序列化成响应（dict → JSON）。

```python
@app.get("/xxx")
async def test_get():
    return {"get message": "Hello"}
```

**（2）路由器 APIRouter**

- 当接口数量变多时，全塞在 `main.py` 里会难以维护，需要**按功能模块分组**；
- 一个 `APIRouter` 就是**管理一组路由的对象**（一个分组），在路由器上注册本组的所有路由，最后统一挂到应用上；

```python
# app/api/routers/product_router.py
product_router = APIRouter()

@product_router.get("/product/{id}")
def get_product(id: int):
    return {"id": id, "name": "product abc"}
```

```python
# main.py —— 注册路由器
app.include_router(product_router, prefix="/v1")
app.include_router(order_router,   prefix="/v2")
```

- `include_router` 的常用参数：
  - `prefix="/v1"`：给该组所有路径统一加前缀（如上例实际路径是 `/v1/product/2`），便于**版本管理**；
  - `tags=["商品"]`：在 `/docs` 文档里给该组接口分组显示；
  - `dependencies=[Depends(verify_token)]`：给整组接口统一加依赖（如鉴权）；

**（3）二者关系**

```
FastAPI app
 ├── include_router(query_router)      ← 路由器（分组）
 │      ├── @query_router.post("/api/query")   ← 路由（接口）
 │      └── ...
 └── include_router(other_router, prefix="/v2")
```

**（4）项目落地**

```python
# app/api/routers/query_router.py
query_router = APIRouter()

@query_router.post("/api/query")
async def search(query_schema: QuerySchema, service: QueryService = Depends(get_query_service)):
    return StreamingResponse(service.search(query_schema.query), media_type="text/event-stream")

# main.py
app = FastAPI(lifespan=lifespan)   # 绑定生命周期
app.add_middleware / @app.middleware("http")  # 请求 id 中间件
app.include_router(query_router)   # 挂载路由器

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8000)
```

**好处**：分组管理、路径前缀统一、便于多人协作（一人一个模块文件，不会冲突）、便于按组加统一依赖和文档标签。
